## 1. 파일럿 입력의 성격 (중요 — 결과 해석에 영향)

입력은 레퍼 이미지에서 크롭한 **이미 픽셀아트인** 소스다(ref-1 얼굴 90px, ref-3 전신 ~112×197 → nearest ×6 업스케일).
즉 **자동 도트화에 가장 유리한 조건**이다. 일반 일러스트(부드러운 셰이딩·그라디언트)를 넣으면 결과는 이보다 나빠진다.
→ 아래 결과는 **품질 상한(best case)** 으로 읽어야 한다.

## 2. 결과 (contact-sheet.png 육안 판정)

| 단계 | 판정 | 근거 |
|---|---|---|
| **카드 (ref-2)** | ✅ **양호** | 프레임·별·뱃지·아트 배치 전부 규격대로. 아트 96×157 도트 → nearest ×2 로 픽셀 격자 보존. 3종 모두 캐릭터 식별 가능. |
| **아바타 64px** | ✅ 양호 | 얼굴·머리장식(뿔/후광/왕관) 식별됨. 팀 링 적용도 정상. |
| **아바타 32px** | 🟡 경계 | 식별은 되나 얼굴 디테일이 뭉갬. ref-1 2단계(손으로 찍은 것)보다 명확히 열위. |
| **아바타 16px** | ❌ **실패** | 3종 모두 형태 붕괴. 아우라=베이지 덩어리, 라그나=회/적 블롭. ref-1 3단계는 실루엣+핵심컬러로 식별되는데 자동 산출은 안 된다. |
| **스프라이트 64/32px** | 🟡 경계 | 전신 실루엣은 남지만 장비·색 구분이 흐려짐. |
| **스프라이트 16/8px** | ❌ **실패** | 아우라 16/8 = 베이지 얼룩, 라그나 8px = 픽셀 3~4개. ref-3 의 2·3단계는 여전히 인식 가능한데 자동 산출은 정보가 남지 않는다. |

**한 줄**: 자동 도트화는 **32px 이상에서만 실용**, **≤16px 은 실패**. 그런데 게임에서 실제로 많이 쓰이는 건 저해상 단계다(피치 위 선수, 소형 아바타).

## 3. 부수 발견 (수정 완료)

| 발견 | 조치 |
|---|---|
| 카드 아트가 작게 박힘 — 세로 캐릭터를 정사각 캔버스에 맞춘 탓 | `dotify(w,h,...)` 로 분리, 카드 아트는 아트영역의 정확히 1/2(96×157)로 도트화 후 nearest ×2 |
| 시그니처 자동 추출이 어두운 의상·그림자를 고름(아우라 → `#675638`) | 채도·중간명도 가중 히스토그램 + 강조색 정규화. 아우라 → `#f5bc47` (레퍼 `#eec830` 과 정합) |
| 설명판 아이콘(r=16)이 프레임에 잘림 | r=9, 설명판 내부 높이에 맞춤 |
| 시그니처 오라가 밝아 어두운 캐릭터(라그나)가 배경에 동화 | 오라 계수 0.16→0.09 로 하향 |

## 4. 남는 한계 (수정으로 못 없앰)

- **시그니처 색 자동 추출은 "면적 최대 채도색"** 이라 테마색과 다를 수 있다. 펭킹킹 → `#c03025`(빨간 망토)가 뽑혔지만 테마는 빙하(레퍼 `#326e8a`).
  → **`incoming/<id>.json` 에 `signature`/`frame` 을 명시하는 것을 권장**, 자동 추출은 폴백으로만.
- **저해상 단계(≤16px)는 원리적으로 자동화 불가.** 픽셀 수가 줄면 "무엇을 남길지"는 정보 축약이 아니라 **작가의 선택**이다.

## 5. 권고 (hero 판정 대기)

1. **SPEC 을 A안(픽셀아트 직접 생성) 권장으로 확정**한다 — 이미 SPEC.md §4 가 A안 권장이며, 이 파일럿이 근거를 실측으로 채웠다.
2. **저해상 단계는 별도 입고**를 권장: hero 가 16px/8px 을 직접 생성(또는 손보정)하면 `incoming/<id>__sprite16.png` 같은 오버라이드 슬롯으로 받도록 파이프라인을 확장한다(미구현 — hero 승인 시 P3 에서).
3. **32px 이상 + 카드**는 자동 파이프라인으로 충분하다 — 그대로 간다.
