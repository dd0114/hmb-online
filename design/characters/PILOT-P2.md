## 1. 파일럿 입력의 성격

레퍼에서 크롭한 **이미 픽셀아트**인 소스(ref-1 얼굴 90px, ref-3 전신 ~112×197 → nearest ×6).
배경은 **불투명 다크 패널**이라 SPEC.md §2 의 투명 배경 요구를 만족하지 못한다 —
즉 배경 분리 난이도는 높고, 도트화 난이도는 낮은(이미 도트라) 혼합 조건이다.

## 2. ① 배경 분리 — **자동 선택 폐기**. 값은 사람이 정한다

다섯 라운드에 걸쳐 자동 선택을 시도했다: 고정 tolerance → 무릎 검출 → 제거량 최대화 →
침식률 제약. **매번 독립 검증이 새로운 실패 모드를 찾았다.** 지표마다 반례가 있었다:

| 지표 | 반례 |
|---|---|
| `largestShare`(파편화) | 배경 잔류를 **못 잡는다**(잔류가 캐릭터에 병합돼 지표를 올림). 연속 침식도 못 잡는다 |
| `holes`(내부 구멍) | 외곽 침식은 구멍을 안 만든다 |
| `erodedPct`(배경 색모델) | **위양성**: 글로우 배경에서 완벽한 컷아웃을 탈락시킴. **위음성**: 그라디언트 배경에서 캐릭터 99.77% 소실을 0.000 으로 통과 |
| 목적함수 `제거량 최대화` | 격자를 넓히면 **캐릭터를 먹는 지점**을 고른다 |

**이건 일반 이미지 매팅 문제이고 이 트랙(테크니컬 아트 = 변환·규격화·검수)의 범위가 아니다.**
그래서 설계를 바꿨다:

- **투명 배경(SPEC §2 권장 경로)이면 이 문제가 아예 없다** — 분리 자체가 불필요.
- **불투명 배경이면 값은 사람이 정한다** — `incoming/<id>.json` 의 `bgTol`.
  `report.json` 의 `tolDiagnostic` 스윕 표를 보고 고르고, **마젠타 렌더로 눈으로 확인**한다.
- **`bgTol` 미지정이면 정확색 제거**(localTol 0/globalTol 0)로 물러나고 크게 경고한다.
  배경이 남을지언정 캐릭터는 사실상 안 먹는다 — **실패가 눈에 보이는 쪽으로만 나게** 하는 설계다.
  (절대 안전은 아니다: 배경색과 **정확히 같은 색**이 캐릭터 안에 있으면 그 부분은 지워진다.
  SPEC §2 가 "캐릭터에 없는 단색"을 요구하는 이유. 그래서 이 경로는 항상 육안 확인을 요구한다.)
  보이지 않는 손상(캐릭터 소실)은 게이트에서 정상으로 오인되지만, 남은 배경 상자는 즉시 보인다.

파일럿 3종은 SPEC 위반 입력(불투명 다크 배경)이므로 **육안 검증 후 값을 고정**했다
(`pilot-crop.mjs`):

| 이미지 | localTol / globalTol | 최대덩어리 |
|---|---|---|
| 라그나 portrait | 9 / 40 | 99.7% |
| 라그나 full | 8 / 60 | 98.3% |
| 아우라 portrait | 11 / 60 | 99.8% |
| 아우라 full | 9 / 140 | 99.8% |
| 펭킹킹 portrait | 14 / 30 | 100% |
| 펭킹킹 full | 11 / 40 | 99.0% |

값이 제각각인 것 자체가 자동화가 어려운 이유다(안전 구간이 소스마다 다르다).

**육안 증빙**: 6장 전부 마젠타 렌더로 확인 — 라그나 다리·공, 아우라 양 날개·후광·공,
펭킹킹 망토·왕관 온전. 배경은 **블록 단위 잔류 없음**(캐릭터 외곽 1~2px AA 프린지는 남는다 —
SPEC §2 가 경고한 항목이고, 투명 배경 입고 시 발생하지 않는다).

> **SPEC §2 의 투명 배경 요구는 이제 "필수"의 의미가 분명해졌다** — 파이프라인이
> 대신 해결해 주지 않는다. 불투명 배경으로 넣으면 사람이 값을 고르고 눈으로 확인해야 한다.

## 3. ② 도트화 — 깨끗한 컷아웃 **12종 전량** 기준

> v6 까지는 표본 3종이었다. hero 요청으로 **레퍼 12캐릭터 전원**을 통과시켜 재측정했다.
> 배경 제거값은 24장 전부 육안 확인해 확정(어두운 캐릭터 4장은 손으로 잡음).

**16px 아바타 판독 결과 (12종)**

| 판정 | 캐릭터 | 공통점 |
|---|---|---|
| ✅ 명확 (4) | 아우라·레오·펭킹킹·바르크 | 갈기/뿔/왕관 = **굵고 독특한 실루엣**, 또는 금발+후광 = 고대비 |
| △ 경계 (4) | 세일·루프스·리야·벨라 | 실루엣 힌트는 남지만 얼굴 소실 |
| ❌ 실패 (4) | 라그나·나츠트·미오·아누비스 | **어두운 머리 + 어두운 복장** = 실루엣이 뭉개짐 |

→ **16px 성공률 4/12(33%).** 3종 표본의 결론(소스 의존)이 12종에서도 그대로 재현됐고,
가르는 기준이 명확해졌다: **실루엣의 굵기와 명도 대비**. 동물형/장식형이 유리하고
어두운 인간형이 불리하다.

**64px·32px 아바타, 카드, 스프라이트 64/32 = 12/12 양호.**
**스프라이트 16/8px = 12/12 실패**(전신은 담을 정보가 많다).

### 원래 3종 표본 (참고)

| 단계 | 라그나 | 아우라 | 펭킹킹 | 판정 |
|---|---|---|---|---|
| **카드 (ref-2)** | ✅ | ✅ | ✅ | **양호 (3/3)** |
| 아바타 64px | ✅ | ✅ | ✅ | **양호 (3/3)** |
| 아바타 32px | ✅ | ✅ | ✅ | **양호 (3/3)** |
| **아바타 16px** | ❌ | ❌ | **△ 경계** | **명확한 성공 0/3** |
| 스프라이트 64/32px | ✅ | ✅ | ✅ | **양호 (3/3)** |
| **스프라이트 16/8px** | ❌ | ❌ | ❌ | **실패 (0/3)** |

**결정 변수는 해상도가 아니라 실루엣 단순성과 색 대비다.**
펭킹킹 16px 아바타는 왕관 실루엣과 파랑/흰 대비 덕에 "무엇인지 짐작은 되지만" 얼굴 디테일은 뭉갠다 —
**△(경계)** 로 낮춰 적는다(v3 은 이걸 ✅ 로 적었으나 확대해 보면 관대한 평가였다).
아우라(섬세한 얼굴·비슷한 명도의 금발/날개)와 라그나(검은 머리 + 어두운 복장)는 명확히 무너진다.
전신 스프라이트는 담을 정보가 많아 ≤16px 에서 3종 모두 실패.

> **8px 단계 주의**: ref-3 범례는 "3단계 ≈ 8×8" 이라 적었지만 **레퍼 자신의 렌더는 60~90px 급**이다.
> 즉 레퍼가 리터럴 8×8 을 제시한 적이 없다. "스프라이트 8px 실패"는 파이프라인 한계이기 이전에
> **규격 해석 문제**일 수 있다 — 8px 단계가 실제로 필요한지 hero 확인 필요.

## 5. 남는 한계

- **시그니처 자동 추출은 "면적 최대 채도색"** 이라 테마색과 어긋난다. 3종 중 **2종 불일치**:

  → **`incoming/<id>.json` 에 `signature`/`frame` 명시 권장**, 자동은 폴백.
- **≤16px 은 소스 의존적**이라 자동 산출을 신뢰할 수 없다(명확한 성공 0/3, 경계 1종).

  `largestShare` 는 높게 나온다(실측: 78% 소실에도 0.986). **최종 안전장치는 지표가 아니라 육안 확인**이다.
- **비-PNG 입력은 macOS `sips` 의존** — 결정론·이식성 미보증(PNG 경로만 검증).
- **레퍼 실측치 충돌**: `measurements.ref103.json` 의 `ref2_frame_scan_y300` 은 절대좌표에 카드 밖 글로우를
  포함해 금테가 과대 측정돼 있고, `row_y:105` 도 재실측(y≈111~114)과 어긋난다.
  → **#103 에 레이즈 완료** (issue #103 comment 5016490989) — 그쪽 소유 파일이라 수정하지 않았다.

## 6. 권고 (hero 판정 대기)

1. **32px 이상 + 카드는 자동 파이프라인으로 충분** — 3/3 통과. 그대로 간다.
2. **≤16px 은 hero 직접 생성/손보정 슬롯 권장** — 명확한 자동 성공이 0/3 이다.
   `incoming/<id>__avatar16.png` 오버라이드로 받고 없으면 자동 폴백(미구현, 승인 시 P3).
   **8px 단계가 실제로 필요한지도 함께 확인 필요**(위 §3 주의 참조).
3. **SPEC §2 투명 배경은 필수** — 파이프라인이 대신 해결해 주지 않는다(자동 선택 폐기). 투명이면 이 문제 자체가 없다.
4. **A안(픽셀아트 직접 생성) 권장 유지** — 저해상까지 신뢰하려면 직접 생성이 안전.
5. **재파일럿 권장**: 도트화 결론은 표본 3종이고, 전부 *이미 픽셀아트*인 소스다.
   hero 가 SPEC 준수(투명 배경) 이미지를 주면 실제 운영 조건으로 다시 측정할 수 있다.
