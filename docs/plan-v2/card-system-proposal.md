**핵심 갭 2가지 (본 제안이 채운다):**
1. **중복이 죽어 있다** — 뽑을수록 무가치. 3개 벤치마크 게임 공통으로 중복은 *성장의 필수 재료*여야 한다.
2. **"같은 선수 더 높은 버전" 축이 없다** — hero 요구의 정중앙. 현 스키마는 선수 identity와 카드 instance가 1:1로 붙어 이걸 표현 못 한다.

### 1.2 조사 결론 (HMB 설계에 직결되는 5개)

1. **버전축과 등급축은 분리하는 게 표준** (컴프야가 명시적). 선수 identity와 카드 instance를 나눠야 "같은 선수를 여러 번 수집·재과금" 구조가 성립. → **baseId / versionId 분리**가 스키마 정답.
2. **중복은 절대 "그냥 분해"만으로 두지 마라.** 3개 게임 공통 최상위 용도 = **한계돌파/진화(상한 돌파)**. 상한 게이팅을 중복에 걸어야 중복에 항구 수요.
3. **"동일 선수 중복"에 프리미엄.** 컴프야(동일선수=버전무관 재료)·FC모바일(동일선수 진화 반값)처럼 **동일선수 중복 > 아무 중복 > 재료**의 3단 위계가 표준.
4. **The Show Live Series가 HMB와 구조적 궁합 최상.** 카드가 외부 성과에 따라 자동으로 자란다 = HMB의 **"선수별 프롬프트→결정론 시뮬 결과"**와 정확히 겹친다. 프롬프트가 잘 먹힌 선수 카드가 성장하는 라이브 곡선은 **경쟁작 누구도 못 하는 HMB 고유 축**이 될 수 있다.
5. **한국 확률형 아이템 법규(2024.3.22 시행)**: 확률·천장·비독립시행 **공개 의무**. 천장/픽업을 넣으면 초기부터 확률 데이터 노출 구조 필요.

## 2. S2 — HMB 맞춤 제안 (3안)

세 안은 **야심·구현비용 오름차순**이며, **누적 단계(A⊂B⊂C)**로 설계했다. 즉 A는 B의 부분집합, B는 C의 부분집합 — 어느 안을 고르든 이후 단계로 확장 가능하고 **PoC 최소 도입분은 세 안 공통으로 A의 일부**다.

세 안 모두 **결정론 불변**(§엔진 규칙)과 **현 5등급·시드 뽑기**를 유지한다. 차이는 "버전축을 도입하느냐"와 "성장을 무엇이 굴리느냐"다.

---

### 안 A — 강화·한계돌파 (성장 중심 · 버전축 없음 · 최소 침습)

**한 줄:** 죽어 있는 `count`를 되살린다. 같은 선수를 여러 장 뽑으면 그 **한 장을 더 강하게**(한계돌파+강화) — 버전은 안 만든다.

- **버전축:** 없음. 선수 = 여전히 1 identity(#84 평면 유지). "같은 호날두 여러 버전"은 **미해결**(hero 요구의 절반만 충족: "더 높은 스탯"은 ○, "더 높은 등급 버전"은 △).
- **등급:** 현 5등급 그대로. 등급은 카드 뽑을 때 고정. 성장은 **등급 내 능력밴드 상단으로 올리고, 한계돌파로 밴드 상한을 소폭 초과** 허용.
- **능력 상승 규칙:** 카드마다 `level`(0→N). 강화 1레벨당 주스탯 소폭↑. **한계돌파** = 동일 선수 중복 소모로 레벨 상한을 단계 개방(예: 기본 +5 → 돌파 시 +10). 최종 능력 = 밴드 기본 + level 보너스(결정론 계수, EngineConfig).
- **중복 처리:** ① **동일 선수 중복 → 한계돌파 재료**(1순위) ② 초과분/타 선수 중복 → **포인트 환급 or 범용 강화 재료**(2순위). 죽은 값 → 항구 수요.
- **배출:** 현 뽑기 그대로. 픽업/천장은 선택(§4).
- **덱 연결:** 현 규칙 그대로(`UNIQUE(deck_id, player_id)`). 변화 없음.
- **프롬프트 시너지:** 낮음 — 카드가 1버전이라 버전별 프리셋 개념 없음. (강화 단계별 해금 프리셋 정도는 가능하나 약함.)
- **스키마 영향(작음):** `user_players`에 `level, limit_break, copies_used` 컬럼 추가. `players` 테이블·data 산출물 **무변경**. #84 v2 평면과 100% 호환.
- **구현비용:** ★☆☆ (ERD 1테이블 컬럼, 서버 강화 API, web 카드 상세 UI, 엔진은 능력계수 반영만).
- **수집 욕망 강도:** ★★☆ — "내 에이스를 키운다" 애착은 생기나, **수집 다양성(다른 버전 호날두)은 없음**.

---

### 안 B — 버전 카드 (버전축 도입 · 수집 중심) 〔권장 타깃〕

**한 줄:** 같은 호날두를 **Base / 시즌·이벤트 / 레전드** 여러 버전으로. **더 높은 버전 = 더 높은 등급의 같은 선수.** hero 요구의 정중앙.

- **버전축:** **baseId(선수 identity) + versionId(카드 instance) 분리.** 한 선수(baseId) 밑에 여러 카드(versionId): `BASE`(기본 등급) · `EVENT`/`SEASON`(상향, 이벤트 배너) · `LEGEND`/`SPECIAL`(전성기 버전, 최상위). 컴프야의 "카드종류축 ≠ 성축"을 차용.
  - **버전축 선택(조사 반영):** HMB PoC엔 실축구 시즌 캘린더가 없으므로 **① 이벤트 배너(한정 발행) + ② 전성기/레전드 버전** 경량 조합을 권장. "커리어 순간(플래시백)"은 실선수 서사와 잘 맞아 v3+ 확장 여지.
- **등급:** 현 5등급 유지. **버전이 곧 등급을 정한다** — 같은 선수 BASE=GOLD면 EVENT 버전=DIA, LEGEND 버전=LEGEND. "더 높은 버전을 갖고 싶다 = 같은 선수의 더 높은 등급 카드를 갖고 싶다"가 자연 성립.
- **능력 상승 규칙:** 버전이 오르면 **더 높은 밴드**로 점프(수집). + 안 A의 강화·한계돌파를 **버전별로** 얹어 밴드 내 성장(육성). 즉 수집(버전↑)과 육성(강화) 이중 축.
- **중복 처리:** ① 동일 **versionId** 중복 → 그 버전 한계돌파 재료 ② 동일 **baseId** 다른 버전 → 상위 버전 합성/승급 재료 or 강화 프리미엄(FC모바일 "동일선수 진화 반값" 차용) ③ 초과분 → 포인트 환급.
- **배출:** 기본 뽑기 + **버전 픽업 배너**(한정 발행 = 이벤트 버전) + **천장**(법규 대응, §4). 상위 버전일수록 낮은 확률.
- **덱 연결 (게임플레이 영향 — hero 결정 필요):** **한 덱에 같은 baseId 2버전 동시 편성 금지** 권장(현실적으로 같은 사람은 한 명). 규칙을 `UNIQUE(deck_id, player_id)` → `UNIQUE(deck_id, base_id)`로 승격. → 유저는 "어느 버전의 호날두를 넣을까"를 선택(전술/프롬프트 최적 버전 고민 = 재미).
- **프롬프트 시너지 (HMB 고유):** **버전별 고유 프롬프트 프리셋** — 예 "레전드 호날두" 버전은 시그니처 프리셋("페널티 박스 안 킬러 본능") 동봉. 경쟁작에 없는 축. 버전 정체성 = 능력 + 프롬프트 성격.
- **스키마 영향(중간):** `players`에 `base_id`(선수 identity), `version`(카드종류), `signature_prompt` 추가. data 산출물이 baseId당 다수 버전 발행. gacha 배너·도감(baseId 그룹핑) 개편. deck UNIQUE 변경.
- **구현비용:** ★★☆ (data 다버전 발행, ERD 스키마 확장+마이그레이션, 서버 배너/승급 API, web 도감 그룹핑+버전 선택 UI, 덱 규칙 변경).
- **수집 욕망 강도:** ★★★ — "같은 선수 더 높은 버전" + 버전별 프롬프트 = hero 요구 정면 충족, 재과금·재수집 동력 최강.

### 안 C — 라이브 성장 (프롬프트·시뮬 연동 하이브리드) 〔북극성 · v3+〕

**한 줄:** 안 B에 **The Show Live Series**를 얹는다. 카드 능력이 **경기 성과(프롬프트가 얼마나 잘 먹혔나)에 따라 결정론적으로 오르내린다.** HMB만이 할 수 있는 축.

- **버전축:** 안 B의 정적 버전 + **라이브 성장 곡선**(동적). 각 카드가 `form`/`chemistry` 같은 라이브 스탯을 갖고, 경기 결과·프롬프트 효과 지표로 변동.
- **성장 엔진:** 육성 조작이 아니라 **플레이가 굴린다.** 결정론 시뮬 결과(골 관여·프롬프트 방향성 반영도 등)를 입력으로 카드가 성장/침체. **양방향**(부진 시 하락)이 긴장감. HMB의 결정론 계약과 궁합 — 라이브 변동도 (seed+결과)로 재현 가능.
- **프롬프트 시너지:** 최상. "이 선수에게 이 프롬프트를 잘 쓰면 카드가 자란다" = 프롬프트 시스템이 곧 성장 시스템. 차별점의 완성형.
- **리스크:** 밸런스·파워크립·결정론 검증 부담 大. PoC 범위 초과.
- **구현비용:** ★★★ (엔진 지표 산출 계약, 라이브 상태 저장·재현, 밸런스 QA 대량). 
- **수집 욕망 강도:** ★★★+ — 고유성 최고, 그러나 **PoC엔 과하다.** B의 상위 확장으로 v3/v4 로드맵에 둔다.

## 4. 공통 설계 요소 (어느 안이든 적용)

- **중복 3단 가치 위계:** 동일 versionId 중복(한계돌파) > 동일 baseId 타버전(승급 프리미엄, 안 B+) > 아무 중복(포인트 환급/범용재료). **낭비 0 체감**(Genshin 초과분 환급 모델).
- **천장·확률(한국법 대응):** 픽업 배너 도입 시 **천장 필수 공개**(예: 상위 버전 N회 미획득 시 확정). 확률표는 economy 파일에 노출(현 구조 확장). 비독립시행이면 그 사실도 공개.
- **결정론 불변:** 강화·돌파·라이브 성장 전부 EngineConfig 계수 + 시드 결정. `Math.random`/`Date.now` 금지, 고정소수. 골든 스냅샷 유지.
- **환급 밸런스:** 초과 중복 환급 포인트는 뽑기 비용 대비 낮게(예: 단뽑 300pt 대비 환급 30~50pt) — 인플레 방지.

## 5. 단계적 도입 경로 (권장)

세 안이 누적집합이므로 **한 방향으로 쌓을 수 있다:**

1. **PoC(지금·저비용):** **안 A** — 죽은 `count`를 한계돌파로 되살리기. **동시에 #84가 `base_id` 컬럼을 nullable로 미리 심어둠**(default = id). 마이그레이션 없이 v3 버전축 준비.
2. **v3:** **안 B** — data가 baseId당 다버전 발행, 픽업 배너·천장·도감 그룹핑·덱 UNIQUE(base_id)·버전 프롬프트 프리셋. hero 요구 완성.
3. **v4(북극성):** **안 C** — 라이브 성장으로 프롬프트=성장엔진 완성.

> **권장:** hero가 "같은 선수 더 높은 버전"을 핵심으로 본다면 **타깃은 안 B**, 단 PoC 첫 삽은 **안 A + baseId 스키마 심기**로 시작해 리스크 없이 B로 확장. (안 A만으로 끝내면 hero 요구의 "버전" 절반이 빈다 — 명시적 선택 필요.)

## 6. hero 결정 필요 지점 (사람 게이트)

1. **타깃 안**: A / B / C 중? (권장: 타깃 B, PoC 시작 A+baseId)
2. **버전축 종류**(안 B/C 선택 시): 이벤트 배너 / 전성기·레전드 / 커리어 순간(플래시백) 중 무엇을 우선?
3. **덱 규칙**: 같은 baseId 2버전 동시 편성 **금지**(권장) vs 허용?
4. **중복 환급**: 포인트 환급 도입? 환급률?
5. **천장·픽업**: PoC부터 넣을지, v3로 미룰지?
