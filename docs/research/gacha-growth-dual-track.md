## 0. 결론 먼저 (3줄)

1. **FM식 유스 아카데미는 우리에게 과하다.** 우리는 가챠 게임이므로 **가챠 네이티브 성장 패턴**(강화/한계돌파 + 기용 성장)이 맞다.
2. hero가 찾는 *"직접 키운 유닛의 가치가 높아지는"* 정답 사례 = **우마무스메**. 뽑은 캐릭터를 **플레이로 키워 고유한 영구 자산(계승 인자)** 으로 만든다.
3. **두 트랙은 이미 우리 설계에 반쯤 있다.** 가챠 트랙 = 카드 시스템 #85 안 A(강화·한계돌파). **경기 트랙만 추가**하면 병렬이 완성된다 — 그리고 그게 우리 차별점(자연어 프롬프트)과 직결된다.

## 1. 사례 조사

### 1.1 ★ 우마무스메 — "직접 키운 유닛이 영구 자산이 된다"의 교과서
가챠 게임이 "육성한 인스턴스에 항구 가치"를 부여한 가장 명확한 사례.

- **두 층이 분리돼 있다** `[출처]`
  - **가챠 = 잠재력 획득**: 캐릭터 + 서포트 카드(육성 보조)를 뽑는다. 뽑기는 *재료*지 완성품이 아니다.
  - **플레이 = 잠재력 실현**: 시나리오를 플레이해 **한 인스턴스를 키운다**. 육성이 끝나면 **그 우마는 더 못 키운다(고정)** — 대신 처음부터 다시 키울 수 있다.
- **키운 결과물이 영구 자산이 된다 = 계승(인자, factor)** `[출처]`
  - 육성 완료 우마는 **계승 인자**를 남기고, 이 인자가 다음 육성의 **출발점을 끌어올린다**(스탯·스킬·적성).
  - 인자는 ★희소도(3성)와 4종 카테고리를 가지며, **혈통을 쌓을수록**(factor stacking) 강력한 전승이 보장된다.
  - 부모 만들 때 **경기를 많이 이길수록** 상성·인자 계승률↑ → *"잘 키운 유닛일수록 더 가치 있는 부모"*.
- **함의**: 뽑기는 복권, **가치는 플레이로 만들어진다.** 같은 SSR이라도 *내가 키운* 인스턴스가 고유하게 값지다. → **가챠와 육성이 경쟁하지 않고 곱해진다.**

### 1.2 기존 벤치마크에서 이중 트랙에 직결되는 것 (재사용 — `card-system-proposal.md` §1)
| 게임 | 경기(플레이) 트랙 | 가챠(수집) 트랙 | HMB 시사 |
|---|---|---|---|
| **MLB The Show — Live Series** | **현실 성적이 카드를 실시간으로 올리고 내린다**(양방향, 육성 조작 아님) | 팩/프로그램으로 카드 획득 | *"내 선수가 오늘 활약하면 카드가 강해진다"* = HMB의 **프롬프트→시뮬 결과**와 구조 동일. **단 The Show는 현실 스탯, 우리는 유저 입력** → 더 강한 애착 |
| **eFootball** | **Progression Points를 유저가 Auto/Manual 배분**해 육성(+스킬 15슬롯) | Featured/Epic 배너 뽑기 | 성장 방향을 유저가 정하는 **배분 UX** 참고 |
| **컴프야 / 이사만루** | 강화 +5 → **한계돌파 +10**(동일선수 중복), 계승(성장자산 이전) | 시즌·픽업 배너 | **가챠 중복이 곧 육성 재료** = 두 트랙의 접착제 |
| **Genshin / Arknights** | (플레이 재화로 돌파·레벨) | **중복 → 상한돌파/잠재 상향**, 초과분 환급 | 중복 처리 3단 배출구(#85 D4) |

### 1.3 5줄 요약 — 가챠 게임의 이중 성장 문법
1. **뽑기는 "완성품"이 아니라 "잠재력"을 준다.** 완성은 플레이가 한다(우마무스메).
2. **중복은 반드시 육성 재료**(한계돌파/잠재). "그냥 분해"만 두면 뽑을수록 무가치(컴프야·Genshin).
3. **경기 기용이 성장 엔진**이 될 수 있다(The Show Live). 이게 우리 차별점과 정확히 겹친다.
4. **성장 방향은 유저가 배분**하면 애착↑(eFootball).
5. **키운 인스턴스에 고유·영구 가치**를 주면 재플레이가 자산 축적이 된다(우마무스메 계승).

## 2. HMB 이중 트랙 모델 (단순화)

> FM의 유스 아카데미(나이·PA·인테이크)를 **버린다.** 대신 가챠 게임 문법으로 두 트랙만 세운다.

```
        ┌─────────── 가챠 트랙 (수집·과금) ───────────┐
뽑기 → 카드 획득 → 중복 → 강화(+5) / 한계돌파(+10)  →  스탯↑
        │                     ↑ 동일선수 중복 = 재료                │
        └───────────────────────┼──────────────────────────┘
                                 │  같은 카드에 두 트랙이 함께 쌓인다
        ┌───────────────────────┼──────────────────────────┐
        │  경기 트랙 (플레이·무과금)                          │
그 카드를 실제 경기에 기용 → 프롬프트 지령대로 활약 → 성장 포인트 → 스탯↑
        │       ↑ 자연어 프롬프트가 성장 방향을 정한다 (HMB 고유)   │
        └──────────────────────────────────────────────────┘
                                 ↓
              "내가 뽑아서(가챠) + 내 문장으로 키운(경기)" 카드 = 고유 자산
```

### 두 트랙의 역할 분담 (경쟁 아님, 곱셈)
| | 가챠 트랙 | 경기 트랙 |
|---|---|---|
| **동력** | 뽑기·중복·포인트(과금 친화) | 기용·프롬프트·승리(무과금 친화) |
| **성장 방식** | 강화 레벨 / 한계돌파(#85 안 A 그대로) | 성장 포인트 → 유저 배분 or 프롬프트 방향 |
| **속도** | 즉시(재료만 있으면) | 느림·누적(경기 반복) |
| **상한** | 한계돌파로 개방 | **강화 상한과 공유**(축 중복 방지 — §3) |
| **감정** | "더 좋은 카드를 뽑았다" | **"내가 키웠다"** ← 가장 강한 애착 |

### HMB만의 결정적 차별 — 경기 트랙 = 자연어 프롬프트
The Show는 **현실 성적**으로 카드가 자란다(유저가 못 만짐). 우마무스메는 시나리오를 반복한다. **HMB는 유저의 프롬프트 지령이 성장을 만든다** — *"측면 파고들어 컷백"* 이라 지시하고 그게 경기에서 실제로 나오면 그 능력치가 자란다. **"내가 쓴 문장으로 키운 선수"** 는 어느 경쟁작도 못 하는 축이다.

## 3. 우리 스키마에 어떻게 (엔진 변경 0)

**대부분 이미 계획에 있다.** 카드 시스템 #85 안 A(강화·한계돌파)가 가챠 트랙 전부다. **경기 트랙 레이어 하나만 추가**한다.

| 트랙 | 필요한 것 | 상태 |
|---|---|---|
| 가챠 | `user_players.level / limit_break / copies_used` | **#85 안 A에 이미 설계됨** |
| 경기 | `user_players.match_xp` (또는 growth_points) + 매치 정산 시 적립 | **신규 — 이 문서 제안** |
| 공유 상한 | 최종 스탯 = 밴드기본 + max/합성(강화보너스, 경기보너스), **공통 캡** | 설계 결정 필요(§4) |

**결정론 정합** (§2-5 무손상):
- 경기 성장은 **server-java 권위** — 매치 정산 트랜잭션에서 `match_xp` 적립, 시드 `hash(userId, cardId, matchId)`, 멱등 플래그.
- **엔진 변경 0.** 성장한 스탯은 다음 매치의 `SelectData` 스냅샷에 반영될 뿐 → **과거 match-log 재생은 bit-identical**.
- **성장 방향 = 프롬프트**는 이미 만드는 `TacticalInput.behavior` 재사용 → **AI 호출 증분 0**(P2-D8 무부하). "좋은 프롬프트" 판정은 AI 채점(비결정론)이 아니라 **match-log 실행 정합**으로(자매 문서 fm-youth-growth §B1 참조).

**핵심 단순화**: 나이·PA·유스 인테이크 **없음**. 실선수 카드 그대로, 두 트랙 다 **같은 카드 인스턴스에 누적**. 별도 엔티티(유스 풀) 불필요 → FM 복잡도 회피.
