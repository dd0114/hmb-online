## 1. 개요 / 비전

**HMB 온라인**은 기존 축구 매니지먼트 시뮬(Football Manager 틀)의 검증된 뼈대 위에, **선수 개개인에게 자연어 AI 프롬프트를 주입**하는 것을 차별점으로 삼는 웹 기반 축구 시뮬 게임이다.

- **플랫폼**: 웹(폰 모드 + 데스크탑 모드) 우선, 추후 **Capacitor** 로 앱 래핑 (`research/rendering.md` §4-3 근거 — WebView 안에서 웹 렌더링 그대로 재사용).
- **비전**: 유저가 슬라이더/드롭다운을 만지는 대신 "감독처럼 말로 지시"하면, AI 가 그 의도를 해석해 전술 인풋으로 환산하고, 결정론 시뮬이 그 인풋으로 경기를 재현한다.
- **핵심 루프**: 선수/포메이션 셋팅 → 자연어 프롬프트 주입 → AI 가 시뮬 인풋 준비 → **스태틱(결정론) 시뮬** → 결과 → (하프타임 개입) → 후반 → 종료·리뷰.
- **온라인 범위**: Phase 1 = 싱글플레이어(vs AI 감독) **PoC 우선**, Phase 2 = 실시간 PvP. PoC 부터 "PvP-ready 경계"를 설계원칙으로 둔다.

## 2. 핵심 차별점 (AI 프롬프트 주입)

기존 FM 은 유저가 팀/개인 지시를 UI 위젯(슬라이더·드롭다운·토글)으로 세팅한다. HMB 는 **동일한 전술 의도를 자연어 프롬프트로 선수 에이전트에 주입**하고, LLM 이 선수 성향(멘탈 속성)·상황 맥락과 결합해 이를 전술 인풋으로 해석한다 (`research/tactics-instructions.md` §4).

- **대체(replace)**: 자연어가 UI 위젯을 완전히 갈음. 예: 멘탈리티 7단계 슬라이더 → "오늘은 무리하지 말고 안정적으로, 실점 안 하는 걸 최우선으로 뛰어라".
- **보완(augment)**: 안전이 중요한 항목(오프사이드 트랩 on/off, 역할 프리셋)은 수치 파라미터를 유지하되 자연어로 뉘앙스 추가.
- **심리/팀톡의 우위**: 사기·팀톡·모멘텀은 정형 UI(감정 드롭다운)보다 자연어로 표현할 때 훨씬 풍부하다 (`research/tactics-instructions.md` §3). 예: "지고 있어도 흔들리지 마라. 후반 15분에 승부를 건다는 마인드로 집중해라".

핵심 매핑 예시 (전체 14종은 `research/tactics-instructions.md` §4):

| FM 지시 | HMB 자연어 프롬프트 | 방식 |
|---------|---------------------|------|
| Mentality (리스크) | "안정적으로, 실점 최우선" | 대체 |
| Pressing + Trigger | "상대 센터백이 볼 잡으면 즉시 두 명이 압박" | 대체 |
| Mark Specific Player | "상대 10번을 밀착 마크해 지워버려라" | 대체 |
| Offside Trap | "라인 맞춰 올려 오프사이드로 걸어라" | 보완(on/off 플래그 병행) |
| Team Talk / Morale | "침착하게 후반에 뒤집는다는 각오로" | 보완(멘탈 속성 결합) |

## 3. 게임 플로우

한 경기는 "개입 가능 구간(OPEN)"과 "관전 잠금 구간(LOCKED)"이 번갈아 나온다. 유저 인풋 창은 **경기 시작 전**과 **하프타임** 두 번뿐이다 (`research/live-intervention-ux.md` §1).

```
[경기전 셋업] OPEN
  · 상대 팀 분석 리포트 · 포메이션/라인업 확정
  · 선수별 AI 프롬프트 입력(프리셋 칩 + 자유 자연어) · 팀 전술 프리셋
  · 입력 마감 타이머 → [킥오프] 확정
        │ 인풋 freeze → AI 가 시뮬 인풋 사전 생성 → 결정론 시뮬에 주입
        ▼
[전반 진행] LOCKED
  · 시뮬 관전(2D 도트/텍스트 커멘터리) · 실시간 이벤트 로그
  · ✎ "다음 개입 초안" 트레이 — 교체·추가 프롬프트를 미리 작성만(커밋 X)
        │ 전반 종료 휘슬
        ▼
[하프타임] OPEN
  · 전반 요약(핵심 이벤트 3~5) + 히트맵/스탯
  · 선수 교체 · 팀톡/추가 프롬프트(초안 승격) · 개별 지시 갱신
  · 입력 마감 타이머 → [후반 시작] 확정
        │ 갱신 인풋 re-freeze → AI 인풋 갱신 → 엔진 재주입(전반 시드에 연속)
        ▼
[후반 진행] LOCKED  · 관전 · 이벤트 로그 · (이번 경기 커밋 창 없음)
        │ 종료 휘슬
        ▼
[경기 종료] · 결과/스탯 · 프롬프트→결과 인과 리뷰 · 다음 경기 학습 저장
```

**하프타임 루프 원칙** (`research/live-intervention-ux.md` §2 사례 B 근거): 하프타임은 "팀톡 + 교체 + 전술 조정"이 한 창에 몰리는 고밀도 순간이므로 **정보(전반요약) → 결정(교체) → 지시(프롬프트)** 순서로 시선을 유도해 인지부하·오조작을 방지한다.

## 4. FM 틀 기능 취합

기존 축구 매니지먼트 시뮬(FM)에서 그대로 가져올 기능 목록. 근거는 `research/tactics-instructions.md`.

| 분류 | 취합 기능 | HMB 반영 방식 |
|------|-----------|---------------|
| **멘탈리티** | 7단계 리스크 다이얼(Very Defensive~Very Attacking) | 자연어 프롬프트로 대체(§2) |
| **국면별 팀 지시** | In Possession(템포/폭/패스직접성) · In Transition(역습/카운터프레스) · Out of Possession(압박/수비라인/오프사이드) | 자연어 대체 + 안전 플래그 보완 |
| **역할(Role)** | 포지션별 전문 역할(딥라잉 플레이메이커, 포처, 인버티드 풀백 등) | 역할 프리셋 + 자연어 뉘앙스 보완 |
| **임무(Duty)** | Defend / Support / Attack | 자연어 대체 |
| **개인 지시** | Take More Risks, Roam From Position, Mark Specific Player, Cross More 등 | 자연어 대체 |
| **교체(Substitution)** | 하프타임·경기중 교체(최대 N명) | 하프타임 교체 보드(§8) |
| **팀톡/사기(Morale)** | 경기전/하프타임/경기후 톡, 개인차 적응, 주장/팀리더 | 자연어 프롬프트 + 선수 멘탈 속성 결합 |
| **선수 속성** | 기술/정신/신체 3축 raw attribute | 시뮬 인풋 및 프롬프트 개인화의 기반값 |

> PoC 에서는 이 중 **멘탈리티·국면 지시·역할/임무·개인 지시·하프타임 교체·팀톡**을 우선 취합하고, 스카우팅·이적·재정·훈련 같은 메타게임은 비범위(§9).

## 5. AI 주입 아키텍처: 방식1 vs 방식2

HMB 의 AI 를 어디에 넣을지 두 방식을 비교한다.

- **방식1** — 프롬프트 → AI 가 시뮬 **인풋을 사전 생성**(팀/선수별 전술 가중치·계수 + 시드) → 그 인풋으로 **스태틱 결정론 시뮬**을 서버가 실행.
- **방식2** — **시뮬 자체가 AI 안에서 돌거나, 매 틱 AI 가 중간 개입**해 행동을 즉석 결정.

| 기준 | 방식1 (AI=사전 인풋 생성 + 결정론 시뮬) | 방식2 (AI=인게임 시뮬/매 틱 개입) |
|------|------------------------------------------|-------------------------------------|
| **결과 정합성** | 높음 — 시드+인풋 고정 시 "같은 인풋=같은 경기" 보장, 리플레이·부정검증 가능 (`research/match-engine.md` §3) | 낮음 — LLM 비결정성으로 매 실행 결과 발산, 재현 불가 |
| **비용** | 낮음 — AI 호출은 경기당 2회(경기전·하프타임)뿐, 이후 시뮬은 순수 계산 | 높음 — 틱마다 LLM 호출(수만 slice/수십 분 = 대량 토큰) |
| **지연(latency)** | 낮음 — 인풋 생성 후 시뮬은 즉시/배속 재생 | 높음 — 틱마다 추론 대기, 실시간 관전 곤란 |
| **구현 난이도** | 중간 — AI 인풋 스키마 + 결정론 엔진 분리 설계 필요 | 높음 — 실시간 LLM 오케스트레이션 + 상태 동기화 난제 |
| **PvP 적합성** | 높음 — 서버 권위 결정론이라 입력 동기화만으로 PvP 확장 (§10) | 낮음 — 양측 LLM 비결정으로 서버 권위 결정론 불가, PvP 부적합 |
| **LLM 연동 자연스러움** | 높음 — 프롬프트→전술 계수 환산은 ESMS식 가중치 모델과 정합 (`research/match-engine.md` §2-2, `_synthesis.md` 연결1) | 중간 — 서사는 풍부하나 통제·검증 어려움 |

### 권장 (추천): 방식1 채택

**HMB 는 방식1(AI 가 시뮬 인풋을 사전 생성 → 결정론 시뮬)을 채택한다.** 근거:

1. 매치엔진 조사(`research/match-engine.md`)의 핵심 결론 — 결정론의 관건은 시드이고, 시드를 인풋의 일부로 고정하면 "같은 인풋=같은 경기"가 보장되어 리플레이·부정검증이 가능하다. 방식2는 이 정합성을 원천적으로 깬다.
2. 비용/지연 — 방식2는 매 틱 LLM 호출로 토큰 비용·추론 지연이 폭증한다. 방식1은 경기당 AI 호출 2회로 억제된다.
3. PvP 이행 — Phase 2 로 가면 서버 권위 결정론이 필수인데, 방식1만이 이를 안전하게 만족한다.

### AI 를 넣는 정확한 지점

방식1 안에서 AI 는 **정확히 두 지점**에만 개입한다 (`research/live-intervention-ux.md` 의 두 OPEN 창과 대응):

- **경기전 인풋 생성**: 유저의 선수별 자연어 프롬프트 + 팀 프리셋 + 라인업 → AI 가 팀/선수별 **전술 가중치 세트(ESMS식 곱셈 계수)** + 초기 시드로 환산. 이 인풋을 결정론 시뮬에 주입해 전반을 재현.
- **하프타임 인풋 갱신**: 전반 이벤트 요약 + 유저의 추가 프롬프트/교체 → AI 가 **후반용 전술 가중치를 갱신**하고, 전반 시드/상태에 연속되도록 후반 인풋을 재주입.
- 관전(LOCKED) 구간에는 AI 호출이 없다. 초안은 로컬 버퍼에만 저장되고 다음 OPEN 창에서만 커밋된다.

## 6. 매치 엔진 설계 방향

근거: `research/match-engine.md`.

- **모델 선택**: FM식 0.25초 물리 slice 는 결정론 유지·검증 비용이 크다. HMB 는 **ESMS식 "능력치 → 팀 총합(Tackling/Passing/Shooting) → 전술 곱셈 계수 → 확률 이벤트"** 를 채택한다. 시간 진행은 **분 단위(또는 포제션 단위) 이벤트 시뮬**이 서버 권위·리플레이에 유리하다 (§5).
- **AI 인풋 접합**: AI 가 자연어 프롬프트에서 환산한 전술 계수가 곧 ESMS의 곱셈 계수(`tactics.dat` 유형) 자리에 들어간다. "인풋만 바꾸고 시뮬은 고정"이라는 HMB 원칙과 정합 (`_synthesis.md` 연결1).
- **결정론/시드**: 확률을 쓰되 **시드를 인풋의 일부로 명시 저장**하고 동일 RNG 를 강제한다. FM 처럼 재미를 위해 "시드를 흔드는" 방식은 배제 — HMB 는 반대로 "같은 인풋이면 같은 결과"가 요구된다 (§3-3).
- **득점 판정**: 슛 → xG → 시드 고정 Poisson 샘플이 경량·설명가능. 무승부/고득점 heavy-tail 보정에 유의 (§2-3).
- **검증/재현**: 초기 시드 + 선택 데이터 + 인풋 로그만 저장하면 headless 재구성으로 경기를 그대로 재현하고 비결정 지점을 flag 할 수 있다 (§3-2). 이것이 §9의 PvP-ready 경계와 §10 서버 권위의 기반.
- **레퍼런스**: **ESMS**(eliben/esms) = 확률 이벤트·전술 계수 로직 참고, **open-football**(ZOXEXIVO, Rust) = 아키텍처/결정론 구현 참고.

## 7. 렌더링 / 표현 방향

근거: `research/rendering.md`.

- **PoC 권장 = 웹 2D 탑다운 도트 뷰**. 경기 표현의 본질은 "이미 계산된 좌표를 화면에 찍는 것"이며, 22명 도트 + 공 1개 = 오브젝트 ~23개라 성능 병목이 사실상 없다 (§1-3). FM 조차 다수 유저가 3D 대신 2D 를 선호한다 (§1-1).
- **기술 스택**: 최저비용 1안 = **HTML Canvas 2D** 직접 구현. 확장성 2안 = **PixiJS v8**(WebGL/WebGPU 스프라이트, 향후 이펙트 여지) 또는 **Phaser 4**(입력·씬·트윈 올인원) (§6).
- **에셋 원가 ≈ 0**: 원/점 도형 + 유니폼 2색 + 번호. 반면 3D 는 엔진이 아니라 **리깅(캐릭터당 $100~$4,000)·모션캡($1,500~$3,000/일)** 에셋이 진짜 비용이라 PoC 예산과 상충 (§2-2). **3D 는 시장 검증 후 확장 옵션**.
- **엔진 출력 접합**: ESMS식 엔진은 물리 좌표를 직접 내지 않으므로, 확률 이벤트 로그(슛/인터셉트/카드)를 만들고 렌더링 좌표는 이벤트를 시각화하는 경량 보간 레이어로 별도 생성한다 (`_synthesis.md` 연결3). PoC 는 텍스트 커멘터리 + 최소 도트 이동으로 충분.
- **반응형**: 피치 종횡비 고정 + 컨테이너 스케일. 폰/데스크탑 카메라·HUD 분기, 배속(즉시결과/1x/2x) 지원. 모바일 30fps 타깃 허용 (§4-1).
- **앱 래핑**: **Capacitor** — WebView 안에서 기존 Canvas/WebGL 렌더링을 그대로 재사용해 렌더링 레이어 재작성이 없다. 가벼운 도트 2D 를 유지하면 저사양 단말 리스크도 낮다 (§4-3).

## 8. 라이브 개입 UX

근거: `research/live-intervention-ux.md`.

- **상태머신(5-상태)**: `PreMatchSetup`(OPEN) → `FirstHalf`(LOCKED) → `HalfTime`(OPEN) → `SecondHalf`(LOCKED) → `FullTime`. 프롬프트 커밋은 OPEN 상태에서만, LOCKED 에서는 초안만 (§4).
- **엔진 계약**: OPEN 커밋 시 프롬프트 페이로드(선수별 자연어 + 프리셋 태그 + 교체)를 엔진에 주입하며 입력 lock. 타이머 만료와 명시적 확정 버튼은 동등한 freeze 트리거. LOCKED 초안은 로컬 버퍼에만 저장.
- **개입 이원화**: 무거운 개입(하프타임 자유 프롬프트) vs 가벼운 개입(상시 프리셋 칩 = FC IQ 퀵택틱 + FM 터치라인 샤우트 하이브리드). B의 8종 프리셋이 칩 콘텐츠 (`research/tactics-instructions.md` §5).
- **폰 모드** — "세로 스텝 위저드"(요약 → 교체 → 프롬프트 3스텝). 원터치 프리셋 칩 우선, 자유 입력은 필요한 선수만 펼침, **음성 입력(STT)** 지원. 타이머 상단 고정, 확정 CTA 하단 고정. 관전 중 초안은 하단 시트(스와이프).
- **데스크탑 모드** — "3분할 대시보드"(좌: 전반요약/히트맵 · 중: 드래그&드롭 교체 보드 · 우: 프롬프트 컴포저). 좌측 요약을 보며 우측에서 바로 자연어 수정 = AgentPitch evolution prompt 를 사람이 수행. 키보드 지향(Tab/Enter/단축키), 자유 입력 비중 높음. 관전 중 우측 패널 상시 열림(비활성).
- **하프타임 인지부하 설계**: 정보→결정→지시 스텝 분리로 FM 하프타임 교체 버그 이력 교훈 반영 (§2 사례 B).

## 9. Phase 1 — 싱글 PoC 범위

**Phase 1** 은 싱글플레이어(vs AI 감독) **PoC** 로, 핵심 루프(프롬프트→AI 인풋→결정론 시뮬→개입→결과)의 재미와 기술 성립성을 검증한다.

### 포함 기능 (In scope)
- 경기 1건 완주 루프: 경기전 셋업 → 전반 → 하프타임 → 후반 → 종료·리뷰.
- 자연어 프롬프트 주입(선수별 자유 입력 + 8종 팀 프리셋 칩) + AI 의 **경기전/하프타임 인풋 생성·갱신**(방식1).
- ESMS식 결정론 매치 엔진(분/포제션 단위 확률 이벤트, 시드 고정), 이벤트 로그 출력.
- 2D 탑다운 도트 뷰 + 텍스트 커멘터리(배속 지원), 폰/데스크탑 반응형.
- FM 취합 최소 세트: 멘탈리티·국면 지시·역할/임무·개인 지시·하프타임 교체·팀톡(§4).
- vs AI 감독: 상대 감독 인풋도 동일 파이프라인(사전 생성 인풋)으로 생성.

### 비범위 (Out of scope — PoC 에서 제외)
- 실시간 PvP·네트워킹·매치메이킹 (→ Phase 2).
- 3D 렌더링/선수 모델·모션캡 (검증 후 확장).
- 스카우팅·이적·재정·훈련·다시즌 커리어 등 메타게임.
- 앱 스토어 배포(Capacitor 래핑은 웹 검증 후).
- 리그/토너먼트 운영, 랭킹/시즌 시스템.

### PvP-ready 경계 (설계원칙)

PoC 부터 **PvP-ready 경계**를 지킨다. 이는 **Phase 1 싱글 단계에서 시뮬을 서버 권위·결정론·입력 로그 재생 가능하게 만들어 두어, Phase 2 에서 네트워킹만 얹으면 되게 하는 원칙**이다 (`research/match-engine.md` §3, `_synthesis.md` 연결5). 구체적으로:

1. **시뮬은 서버(권위)에서 실행** — 클라이언트는 결과 재생만. 싱글에서도 클라이언트 계산 금지.
2. **결정론 + 명시 시드** — 시드를 인풋의 일부로 저장, 동일 RNG 강제 → 같은 인풋=같은 경기.
3. **입력 로그 재생 가능** — 초기 시드 + 선택 데이터 + 프레임/틱별 인풋 시퀀스만 저장하면 headless 재현·부정검증 가능.
4. **AI 인풋 스키마를 네트워크 페이로드로 설계** — 경기전/하프타임 인풋을 직렬화 가능한 계약으로 정의(§5 엔진 계약), Phase 2 에서 그대로 상대에게 동기화.

즉 PoC 는 "싱글이지만 내부 구조는 이미 PvP 를 위한 서버 권위 결정론"으로 만든다.

## 10. Phase 2 — 실시간 PvP 로드맵

**Phase 2** 는 두 유저 감독이 실시간으로 맞붙는 PvP 를 얹는다. Phase 1 의 PvP-ready 경계 덕분에 시뮬 코어 재작성 없이 **네트워킹 계층 추가**가 주 작업이 된다.

- **서버 권위 시뮬**: 경기 시뮬은 전적으로 서버에서 결정론 실행. 양측 클라이언트는 동일 결과를 재생(재계산 금지). 방식1 채택(§5)이 이를 가능케 한 핵심.
- **입력 동기화**: 양측의 경기전/하프타임 AI 인풋(직렬화된 전술 가중치 + 교체)을 서버가 수집·검증 후 동일 시드로 시뮬. 두 유저가 각자 프롬프트를 커밋하면 서버가 합쳐 한 경기를 산출.
- **락스텝 vs 서버시뮬 고려**: HMB 는 실시간 조작이 아니라 "OPEN 창에서만 커밋"하는 턴제성 개입이라 순수 락스텝보다 **서버 권위 시뮬(서버가 결정론 계산 후 결과 브로드캐스트)** 이 자연스럽다. state hash 검증·headless replay 로 desync·부정 탐지 (`research/match-engine.md` §3-2).
- **동시성 처리**: 양측 하프타임 개입 창의 타이머 동기화, 한쪽 미입력 시 이전 인풋 유지 등 규칙 정의.
- **확장 항목**: 매치메이킹/랭킹, 리플레이 공유(입력 로그 기반), 관전 모드.
