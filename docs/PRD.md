## 1. 개요 / 비전

**HMB 온라인**은 기존 축구 매니지먼트 시뮬(Football Manager 틀)의 검증된 뼈대 위에, **선수 개개인에게 자연어 AI 프롬프트를 주입**하는 것을 차별점으로 삼는 웹 기반 축구 시뮬 게임이다. 장기적으로는 **선수 카드 수집(FC 온라인형) + 덱 구성 메타게임**을 얹어 지속성과 수익모델을 확보한다.

- **플랫폼**: 웹(폰 모드 + 데스크탑 모드) 우선, 추후 **Capacitor** 로 앱 래핑 (`research/rendering.md` §4-3).
- **비전**: 유저가 슬라이더/드롭다운을 만지는 대신 "감독처럼 말로 지시"하면, AI 가 그 의도를 **선수별 행동 파라미터**로 해석하고, **결정론 공간 시뮬**이 그 인풋으로 22명이 실제로 움직이는 경기를 재현한다.
- **매치 엔진 = Tier B(축소 공간 에이전트)**: 선수가 피치 좌표를 갖고 1초 틱마다 이동/패스/슛/압박을 판단한다. "풀백은 사이드로 올라가 공격 창출", "더 침투해라" 같은 위치·움직임 지시가 **실제 움직임으로 보이게** 하는 것이 핵심(§7). FM식 0.25초 마이크로 물리(Tier C)는 장기 목표(Backlog).
- **핵심 루프(경기)**: 선수/포메이션 셋팅 → 자연어 프롬프트 주입 → AI 가 행동 파라미터 인풋 생성 → **결정론 공간 시뮬** → 결과 → (하프타임 개입) → 후반 → 종료·리뷰.
- **로드맵**: Phase 1 = 싱글(vs AI 감독) **PoC** → Phase 2 = **매니지먼트 메타(덱 수집+프리셋 · 스카우팅·이적·재정·훈련)** → Phase 3 = **실시간 PvP**. Tier C 물리 고도화·3D·리그·랭킹·앱배포는 Backlog. **PoC 부터 "PvP-ready 경계"를 설계원칙으로.**

## 2. 핵심 차별점 (AI 프롬프트 주입)

기존 FM 은 유저가 팀/개인 지시를 UI 위젯(슬라이더·드롭다운·토글)으로 세팅한다. HMB 는 **동일한 전술 의도를 자연어 프롬프트로 선수 에이전트에 주입**하고, LLM 이 선수 성향(속성)·상황 맥락과 결합해 이를 **선수별 행동 파라미터**로 해석한다 (`research/tactics-instructions.md` §4). 공간 엔진(§7)이라 위치·움직임 지시가 밋밋한 계수가 아니라 **실제 피치 위 행동**으로 나타난다.

- **대체(replace)**: 자연어가 UI 위젯을 완전히 갈음. 예: 멘탈리티 슬라이더 → "무리하지 말고 안정적으로, 실점 최우선".
- **보완(augment)**: 안전이 중요한 항목(오프사이드 트랩, 역할 프리셋)은 수치 파라미터를 유지하되 자연어로 뉘앙스 추가.
- **위치·움직임 지시의 표현력(신규 강점)**: "풀백 오버랩", "하프스페이스 침투", "상대 6번 봉쇄" 같은 공간 지시가 Tier B 에서 **다른 움직임**으로 구분되어 나타난다. Tier A(추상 통계)에서는 전부 계수로 뭉개져 불가능했던 부분.
- **심리/팀톡의 우위**: 사기·팀톡·모멘텀은 자연어로 표현할 때 훨씬 풍부 (`research/tactics-instructions.md` §3).

핵심 매핑 예시 (전체 14종은 `research/tactics-instructions.md` §4):

| FM 지시 | HMB 자연어 프롬프트 | Tier B 반영(행동 파라미터) |
|---------|---------------------|----------------------------|
| Mentality | "안정적으로, 실점 최우선" | 팀 defensiveLineHeight↓, 선수 supportDepth↓, forwardRunFreq↓ |
| Overlap / 풀백 전진 | "풀백은 사이드로 올라가 공격 창출" | 해당 풀백 widthTendency↑, forwardRunFreq↑, basePosition x↑ |
| 침투(penetration) | "더 침투해라" | forwardRunFreq↑, supportDepth↑, 채널 런 트리거 on |
| Pressing + Trigger | "센터백이 볼 잡으면 즉시 두 명이 압박" | pressAggression↑, team.pressingScheme.triggerLine↑ |
| Mark Specific Player | "상대 10번을 밀착 마크" | markTarget=상대10, positioningFreedom(마커) 재정의 |
| Offside Trap | "라인 맞춰 올려 오프사이드" | team.offsideTrap=on(보완 플래그) + defensiveLineHeight↑ |

## 3. 게임 플로우

한 경기는 "개입 가능 구간(OPEN)"과 "관전 잠금 구간(LOCKED)"이 번갈아 나온다. 유저 인풋 창은 **경기 시작 전**과 **하프타임** 두 번뿐이다 (`research/live-intervention-ux.md` §1).

```
[경기전 셋업] OPEN
  · 상대 팀 분석 리포트 · 포메이션/라인업 확정
  · 선수별 AI 프롬프트 입력(프리셋 칩 + 자유 자연어) · 팀 전술 프리셋
  · 입력 마감 타이머 → [킥오프] 확정
        │ 인풋 freeze → AI 가 행동 파라미터 인풋 생성 → 결정론 공간 시뮬에 주입
        ▼
[전반 진행] LOCKED
  · 시뮬 관전(2D 실제 움직임 재생 + 이벤트 커멘터리) · 실시간 이벤트 로그
  · ✎ "다음 개입 초안" 트레이 — 교체·추가 프롬프트를 미리 작성만(커밋 X)
        │ 전반 종료 휘슬
        ▼
[하프타임] OPEN
  · 전반 요약(핵심 이벤트 3~5) + 히트맵/스탯
  · 선수 교체 · 팀톡/추가 프롬프트(초안 승격) · 개별 지시 갱신
  · 입력 마감 타이머 → [후반 시작] 확정
        │ 갱신 인풋 re-freeze → AI 인풋 갱신 → 엔진 재주입(전반 시드·경기상태에 연속)
        ▼
[후반 진행] LOCKED  · 관전 · 이벤트 로그 · (이번 경기 커밋 창 없음)
        │ 종료 휘슬
        ▼
[경기 종료] · 결과/스탯 · 프롬프트→움직임→결과 인과 리뷰 · 다음 경기 학습 저장
```

**하프타임 루프 원칙** (`research/live-intervention-ux.md` §2): 하프타임은 "팀톡 + 교체 + 전술 조정"이 몰리는 고밀도 순간이므로 **정보(전반요약) → 결정(교체) → 지시(프롬프트)** 순서로 시선을 유도해 인지부하·오조작 방지.

## 4. FM 틀 기능 취합

기존 축구 매니지먼트 시뮬(FM)에서 그대로 가져올 기능 목록. 근거는 `research/tactics-instructions.md`.

| 분류 | 취합 기능 | HMB 반영 방식 |
|------|-----------|---------------|
| **멘탈리티** | 7단계 리스크 다이얼 | 자연어 → 팀/선수 행동 파라미터로 대체(§2) |
| **국면별 팀 지시** | In Possession(템포/폭/직접성) · Transition(역습/카운터프레스) · Out of Possession(압박/라인/오프사이드) | 자연어 대체 + 안전 플래그 보완 |
| **역할(Role)** | 포지션별 전문 역할 | 역할 프리셋(basePosition+기본 behavior) + 자연어 보완 |
| **임무(Duty)** | Defend / Support / Attack | supportDepth·forwardRunFreq 로 매핑 |
| **개인 지시** | Take More Risks, Roam, Mark, Get Forward 등 | 행동 파라미터로 대체(§6) |
| **교체(Substitution)** | 하프타임·경기중 교체 | 하프타임 교체 보드(§9) |
| **팀톡/사기(Morale)** | 경기전/하프타임/후 톡 | 자연어 + 선수 멘탈 속성 결합(mentalModifier) |
| **선수 속성** | 기술/정신/신체 3축 raw attribute | 공간 시뮬 판정·행동의 기반값 |

> PoC 는 **멘탈리티·국면 지시·역할/임무·개인 지시·하프타임 교체·팀톡**을 우선 취합. 스카우팅·이적·재정·훈련은 Phase 2(§10).

## 5. AI 주입 아키텍처: 방식1 채택 (확정)

AI 를 시뮬 어디에 넣을지의 결정. **방식1을 확정 채택**한다. (엔진이 Tier A든 B든 이 결정은 동일 — AI 는 인풋만 만들고 시뮬은 결정론.)

- **방식1 (채택)** — 프롬프트 → AI 가 **행동 파라미터 인풋을 사전 생성** → 그 인풋으로 **결정론 공간 시뮬**을 서버가 실행.
- **방식2 (기각)** — 시뮬 자체가 AI 안에서 돌거나 매 틱 AI 가 중간 개입.

| 기준 | 방식1 (채택) | 방식2 (기각) |
|------|------|------|
| **결과 정합성** | 높음 — 시드+인풋 고정 시 "같은 인풋=같은 경기", 리플레이·부정검증 가능 (`research/match-engine.md` §3) | 낮음 — LLM 비결정으로 매 실행 발산 |
| **비용** | 낮음 — AI 호출 경기당 2회 | 높음 — 틱마다 LLM 호출 |
| **지연** | 낮음 — 인풋 생성 후 즉시/배속 재생 | 높음 — 틱마다 추론 대기 |
| **구현 난이도** | 중간 — 인풋 스키마 + 결정론 엔진 분리 | 높음 — 실시간 LLM 오케스트레이션 |
| **PvP 적합성** | 높음 — 서버 권위 결정론 (§11) | 낮음 — 양측 LLM 비결정 |

> **결정론에 대한 정정(v1.1)**: 공간 엔진(Tier B)도 결정론으로 만들 수 있다. 진짜 어려운 결정론은 *여러 기계의 물리 연산이 비트 단위로 일치해야 하는 P2P 락스텝*인데, HMB 는 **서버가 시뮬을 한 번만 실행하고 클라는 재생**하므로 "같은 서버·같은 인풋 → 같은 결과"만 보장하면 된다. 이는 **시드 고정 + 고정소수(fixed-point) 연산**으로 달성한다(§7·§11). 즉 공간 엔진이 결정론을 막지 않는다.

### AI 를 넣는 정확한 지점 (2곳)

- **경기전 인풋 생성**: 유저의 선수별 자연어 프롬프트 + 팀 프리셋 + 라인업 → AI 가 팀/선수별 **행동 파라미터 세트**(§6) + 초기 시드로 환산.
- **하프타임 인풋 갱신**: 전반 요약 + 추가 프롬프트/교체 → AI 가 후반용 행동 파라미터를 갱신, 전반 시드/경기상태에 연속되게 재주입.
- 관전(LOCKED) 구간엔 AI 호출 없음. 초안은 로컬 버퍼에만, 다음 OPEN 창에서만 커밋.

## 6. AI 인풋 스키마 & LLM 연동 (Tier B 행동 파라미터)

방식1의 심장은 **"자연어 프롬프트 → 구조화된 행동 파라미터"** 변환이다. Tier B 는 계수 몇 개가 아니라 **선수의 공간 행동을 규정하는 파라미터 세트**를 출력하므로 프롬프트 표현력이 크게 늘어난다.

### 6-1. `TacticalInput` 스키마 (직렬화 계약)

AI 는 자유 텍스트가 아니라 **고정 스키마 JSON** 을 출력한다(구조적 출력 강제). 이 JSON 이 곧 공간 엔진 입력이자 PvP 네트워크 페이로드(§12).

```
TacticalInput {
  seed: uint64,                          // 결정론 시드(인풋의 일부)
  team: {
    formation: enum,                     // 4-3-3, 4-2-3-1 ...
    defensiveLineHeight: 0..1,           // 수비 라인 높이
    compactness: 0..1,                   // 팀 간격(밀집도)
    tempo: 0..1,
    width: 0..1,
    pressingScheme: { intensity: 0..1, triggerLine: 0..1 },  // 어디서부터 압박
    offsideTrap: bool                    // 안전 플래그(보완 항목)
  },
  players: [{
    playerId,
    role: enum, duty: defend|support|attack,
    basePosition: { x: 0..1, y: 0..1 },  // 포메이션 슬롯(정규화 좌표)
    behavior: {
      positioningFreedom: 0..1,          // roam — 위치 이탈 정도
      forwardRunFreq: 0..1,              // 침투 빈도(오프더볼 전진 런)
      widthTendency: 0..1,               // 사이드로 벌림(풀백 오버랩)
      supportDepth: 0..1,                // 공격 가담 깊이
      pressAggression: 0..1,             // 개인 압박 적극성
      passRisk: 0..1, passDirectness: 0..1,
      dribbleTendency: 0..1, shootTendency: 0..1
    },
    markTarget?: playerId,               // 전담 마크
    mentalModifier: -1..+1              // 팀톡·사기 반영
  }],
  meta: { generatedAt, promptHash }      // 재현·감사용
}
```

- 범위·enum 은 **엔진이 검증·클램프**. AI 산출이 스키마 위반이면 1회 재요청 → 실패 시 역할 프리셋 기본값 폴백.
- 하프타임 갱신은 `team`·`players[].behavior`·`basePosition`·교체만 델타 적용(시드·경기상태 연속).

### 6-2. LLM
- **모델**: **Claude**. 프롬프트→`TacticalInput` 변환에 **tool-use / JSON schema 강제**.
- **PoC 티어**: **Claude Sonnet**(비용·지연 균형). 애매·복잡 케이스만 상위 모델 에스컬레이션.
- **호출 예산**: 경기당 최대 2회(경기전+하프타임) × 양팀. 동일 프롬프트+선수풀 조합 캐시.

### 6-3. 밸런스 원칙 — "단일 최적 프롬프트" 방지
1. **선수 종속성**: 같은 프롬프트도 선수 raw 속성에 따라 파라미터·결과가 다르게(느린 풀백의 오버랩은 역습 실점 리스크↑).
2. **상대 맥락 종속성**: 상대 포메이션·전술이 AI 해석에 입력 → 상성.
3. **소프트 캡 + 시드 노이즈**: 극단 파라미터는 체력·응집도·수비 노출 페널티. 결정론 유지한 채 시드 고정 노이즈로 분산.
4. **검증 목표(§12)**: 서로 다른 프롬프트 전략이 서로 다른/납득 가능한 결과 + **위치 지시가 실제 다른 움직임**을 만드는지 계측.

## 7. 매치 엔진 설계 방향 — Tier B 축소 공간 에이전트

근거: `research/match-engine.md`(듀얼/확률 판정은 ESMS·xG 참고, 시간진행은 §1-1 slice 를 1초로 축소).

### 7-1. 모델 개요
- **피치 = 연속 2D 좌표**(정규화 105×68). 선수 22명 + 공 1개가 각자 위치·속도를 갖는다.
- **틱 = 1초**(FM 0.25초의 축소). 90분 ≈ 5,400틱, CPU 매우 경량(헤드리스로 수초 내 완주).
- 매 틱: **인식(perceive) → 판단(decide) → 실행(act) → 경합 해상(resolve)** 순으로 22 에이전트가 행동. 물리는 "공/선수 2D 위치·속도 + 단순 이동" 수준(정교한 충돌·마이크로 물리 없음 = Tier C 와의 경계).

### 7-2. 핵심 모듈
- `pitch.ts` — 좌표계·구역·거리/각도 유틸(고정소수).
- `ball.ts` — 공 이동(패스/슛 궤적, 감속). fixed-point.
- `perception.ts` — 각 선수의 주변 인식(가까운 동료/상대, 공간, 압박도, 패스 옵션).
- `decision.ts` — 행동 선택. 볼 소유자: {슛(사거리·각도), 패스(최적 옵션), 드리블(공간), 홀드}; 오프더볼: 역할 위치로 이동 + 침투 런(forwardRunFreq) + 폭 조정(widthTendency); 수비: 라인 유지/마크/압박(pressAggression·triggerLine)/커버. **선택은 [선수 속성 + behavior 파라미터 + 상황]의 시드 고정 가중 확률**.
- `contest.ts` — 볼 경합/태클/인터셉트/슛→xG→득점 판정. 능력치 대결을 확률화(ESMS/xG 참고). 예: 패스 성공 = f(passer.passing, 거리, 압박, 레인 내 수비수 positioning).
- `rng.ts` — 시드 PRNG(mulberry32/xorshift), 전역·`Math.random` 금지. RNG 인스턴스를 관통.
- `fixedmath.ts` — 위치·속도·누적을 **정수 스케일 고정소수**로 계산(부동소수 비결정 격리).
- `hash.ts` — 틱별 state hash(FNV-1a)로 결정론·desync 검증.
- `match.ts` — `runFirstHalf` / `resumeSecondHalf`. 하프타임 델타 주입 후 **전반 종료 시점의 좌표·속도·스코어·RNG 상태를 이어받아** 후반 재개.

### 7-3. 틱 루프 의사코드
```
function runTick(rng, state, homeInput, awayInput):
  updateBall(state.ball)                       // 궤적·감속 (fixed-point)
  for p in state.players:                      // 22명
     ctx = perceive(p, state)                  // 주변·압박·옵션
     action = decide(rng, p, ctx, inputOf(p))  // 속성 + behavior 파라미터 가중 확률
     apply(p, action, state)                   // 이동/패스개시/슛/압박
  resolveContests(rng, state)                  // 볼 경합·태클·인터셉트·슛→xG→득점
  applyFatigue(state)                          // 소프트캡: 극단 behavior 페널티(§6-3)
  emitEvents(state) ; state.hash = hash(state)
```
- 접합: `behavior.forwardRunFreq/widthTendency/basePosition` 이 오프더볼 이동을 좌우 → **"풀백 올라가라"가 실제 x좌표 상승 + 오버랩 런으로 관측**. `team.defensiveLineHeight/pressingScheme` 는 수비 라인·압박 좌표에 직접 반영.
- 소프트캡: 극단 전진(모두 침투)은 뒤 공간 노출 → 역습 실점 확률↑. "단일 최적 프롬프트" 방지의 엔진측 착지점.

### 7-4. 결정론·재현 계약
- 시드를 `TacticalInput.seed` 로 인풋 일부로 고정, 동일 RNG 강제. fixed-point 로 부동소수 발산 차단.
- **재현 세트 = `(seed + selectData + inputLog + EngineConfig 버전)`**. `inputLog`=[경기전 TacticalInput, 하프타임 델타]. 이 넷이면 server 없이 engine headless 로 100% 동일 재생. config 는 버전 태깅(§7-6).
- **결정: 단일 RNG 스트림 순차 소비 + 골든 스냅샷 잠금**(단순성). fork 는 필요 시 도입.

### 7-5. 레퍼런스
- 시간진행: FM slice(`research/match-engine.md` §1-1)를 1초로 축소·단순화.
- 듀얼/득점: ESMS 확률 가중(§2-2) + xG(§2-3).
- 결정론 아키텍처: open-football(Rust) 참고(§4). PoC 는 TS.

### 7-6. Configuration / 튜닝 레이어 (모든 magic number 격리)
- 엔진의 모든 튜닝 값은 **하드코딩 금지 → `EngineConfig` 객체로 격리**해 코드 수정 없이 조정 가능하게 한다(FM `tactics.dat` 데이터드리븐 철학과 동일).
- **포함 항목(예)**: 틱 해상도(`msPerTick`, 기본 1000), 피치 치수, **좌표 모드(`continuous` | `grid` + `gridSize`)**, 인식 반경, decision 가중치, contest 확률 계수(패스/태클/xG), 소프트캡 페널티, 체력 감가율, 고정소수 스케일, 포메이션 정의.
- `BalanceConfig` 는 밸런스-sim 전용 노브를 별도 분리. UI 튜닝 값(배속·타이머)은 `UIConfig`.
- **재현 계약에 config 포함**: 경기는 특정 `EngineConfig` 버전 하에서 재현된다. config 를 바꾸면 과거 매치 재현은 그 버전으로 핀해야 하므로 **config 를 버전 태깅하고 재현 번들(§7-4)에 포함/참조**한다.
- 즉 "틱 1초→0.5초", "연속→그리드", 범위·계수 조정은 전부 **config 변경 한 번**으로 되어야 하고, 로직 코드는 config 를 읽을 뿐이다.

## 10. 매니지먼트 메타게임 — 덱 수집 + 프리셋 (Phase 2)

PoC 검증 후 바로 다음 순위의 지속성·수익 레이어. 방향 = **"수집 + 프리셋 둘 다"**.

### 10-1. 선수 카드 수집 (Collection)
- 선수를 카드/자산으로 보유. 획득: 팩(랜덤)·마켓(거래)·시즌 보상·스카우팅. (수익 후크: 팩/시즌패스 — 후속 결정)
- 카드 = 선수 + raw 속성(기술/정신/신체) + 성장 상태. **훈련**으로 성장, **재정**으로 이적/영입.

### 10-2. 덱(프리셋) 구성 (Preset)
- **덱 = 스쿼드(선발+벤치) + 포메이션 + 팀 전술 프리셋 + 선수별 프롬프트 프리셋**을 하나로 저장.
- 여러 덱 저장 + 상대·상황별 **원클릭 전환**(예: "수비 안정 덱", "총공세 덱").
- 경기전 셋업(§3)에서 덱을 불러오면 라인업·프롬프트 일괄 세팅 → 개입 창 시간 절약.

### 10-3. 연결 시스템
- **스카우팅**: 상대/시장 선수 분석 → 카드 획득 후보 + 경기전 상대분석 리포트 소스.
- **이적/재정**: 카드 거래·영입 경제, 예산 관리.
- **훈련**: 카드 속성 성장 → §6 밸런스의 "선수 종속성"에 직접 영향.

> Phase 2 는 §6 `TacticalInput` 이 `playerId` 기반이라 카드 시스템과 자연 접합(스키마 재설계 불필요).

## 11. 기술 스택 & 결정론 구현 (결정)

- **후순위 최적화**: 성능 한계 시 `packages/engine` 을 Rust(open-football 참고) 포팅. PoC 는 TS 로 충분(1초 틱 × 5,400 = 매우 경량).

## 12. Phase 1 — 싱글 PoC 범위

**Phase 1** 은 싱글(vs AI 감독) **PoC** 로, 핵심 루프(프롬프트→행동 파라미터→**공간 시뮬**→개입→결과)의 **재미와 기술 성립성**을 검증한다.

### 포함 기능 (In scope)
- 경기 1건 완주 루프: 경기전 셋업 → 전반 → 하프타임 → 후반 → 종료·리뷰.
- 자연어 프롬프트 주입(선수별 자유 입력 + 8종 프리셋 칩) + AI 경기전/하프타임 인풋 생성·갱신(방식1, §5·§6).
- `TacticalInput` 행동 파라미터 스키마 + Claude structured output 변환.
- **Tier B 공간 시뮬**: 1초 틱, 22 에이전트 인식→판단→실행, 좌표 기반, 시드 고정 결정론(§7).
- **2D 실좌표 재생**(PixiJS) + 이벤트 커멘터리(배속), 폰/데스크탑 반응형.
- FM 취합 최소 세트(멘탈리티·국면·역할/임무·개인 지시·하프타임 교체·팀톡, §4).
- vs AI 감독: 상대 인풋도 동일 파이프라인.
- **검증 계측**: (a) 움직임이 그럴듯한가(정성), (b) 위치·움직임 프롬프트가 다른 움직임/결과를 만드는가, (c) 단일 최적 전략으로 수렴 안 하는가(§6-3).

### 비범위 (Out of scope)
- **Phase 2 로**: 덱 수집·프리셋, 스카우팅·이적·재정·훈련(PoC 직후 착수).
- **Phase 3 로**: 실시간 PvP·네트워킹·매치메이킹.
- **Backlog**: Tier C(0.25초 마이크로 물리 고도화), 3D 렌더링/모델·모션캡, 리그·랭킹·시즌, 앱스토어 배포.

### PvP-ready 경계 (설계원칙)
PoC 부터 지킨다. **싱글 단계에서 시뮬을 서버 권위·결정론·입력 로그 재생 가능하게 만들어, Phase 3 에서 네트워킹만 얹으면 되게 하는 원칙**:
1. **시뮬은 서버(권위)에서 실행** — 클라는 재생만.
2. **결정론 + 명시 시드 + 고정소수** — 같은 인풋=같은 경기.
3. **입력 로그 재생 가능** — `(seed+selectData+inputLog)` headless 재현·부정검증.
4. **AI 인풋 스키마를 네트워크 페이로드로 설계** — §6 `TacticalInput` 직렬화 계약, Phase 3 에서 그대로 동기화.

## 13. 로드맵

| Phase | 범위 | 핵심 산출 | 검증 기준 |
|-------|------|-----------|-----------|
| **1. PoC** | 싱글(vs AI) 핵심 루프 | Tier B 공간 결정론 엔진 + 프롬프트→행동파라미터 파이프라인 + 2D 실좌표 재생 + 라이브 개입 | 경기 완주 + 움직임 그럴듯 + 위치 프롬프트가 다른 움직임·결과 + 단일최적 비수렴 + 100% 재현 |
| **2. 매니지먼트 메타** | 덱 수집+프리셋 · 스카우팅·이적·재정·훈련 | 카드 시스템 + 덱 프리셋 + 경제 루프 | 수집→덱→경기 순환 성립, 리텐션 훅 |
| **3. 실시간 PvP** | 두 감독 실시간 대전 | 서버 권위 시뮬 + 입력 동기화 + 매치메이킹 | 코어 재작성 없이 네트워킹만으로 동작, desync 0 |
| **Backlog** | Tier C 물리 고도화 · 3D · 리그/랭킹/시즌 · 앱스토어 | — | Phase 1~3 검증 후 재평가 |

### Phase 3 실시간 PvP 고려사항 (미리보기)
- **서버 권위 시뮬**: 서버 결정론 실행, 양측 클라 재생. 방식1(§5)·고정소수 결정론이 이를 가능케 함.
- **입력 동기화**: 양측 경기전/하프타임 `TacticalInput` 을 서버가 수집·검증 후 동일 시드로 산출.
- **락스텝 vs 서버시뮬**: HMB 는 "OPEN 창에서만 커밋"하는 턴제성 개입이라 **서버 권위 시뮬**이 자연스럽다. state hash·headless replay 로 desync·부정 탐지.

### Tier C 승격 조건 (Backlog)
Tier B 로 재미·성립성이 검증되고 상용화 단계에서 더 높은 표현력이 필요하면, 틱을 0.25초로 낮추고 마이크로 물리·충돌을 도입한다. 엔진 인터페이스(인풋→MatchLog)는 동일하게 유지해 교체 가능하게 설계.
