## 1. 개요 / 비전

**HMB 온라인**은 기존 축구 매니지먼트 시뮬(Football Manager 틀)의 검증된 뼈대 위에, **선수 개개인에게 자연어 AI 프롬프트를 주입**하는 것을 차별점으로 삼는 웹 기반 축구 시뮬 게임이다. 장기적으로는 **선수 카드 수집(FC 온라인형) + 덱 구성 메타게임**을 얹어 지속성과 수익모델을 확보한다.

- **플랫폼**: 웹(폰 모드 + 데스크탑 모드) 우선, 추후 **Capacitor** 로 앱 래핑 (`research/rendering.md` §4-3 — WebView 안에서 웹 렌더링 그대로 재사용).
- **비전**: 유저가 슬라이더/드롭다운을 만지는 대신 "감독처럼 말로 지시"하면, AI 가 그 의도를 해석해 전술 인풋으로 환산하고, **결정론 시뮬**이 그 인풋으로 경기를 재현한다.
- **핵심 루프(경기)**: 선수/포메이션 셋팅 → 자연어 프롬프트 주입 → AI 가 시뮬 인풋 준비 → **스태틱(결정론) 시뮬** → 결과 → (하프타임 개입) → 후반 → 종료·리뷰.
- **로드맵**: Phase 1 = 싱글(vs AI 감독) **PoC** → Phase 2 = **매니지먼트 메타(덱 수집+프리셋 · 스카우팅·이적·재정·훈련)** → Phase 3 = **실시간 PvP**. 3D·리그·랭킹·앱배포는 Backlog. **PoC 부터 "PvP-ready 경계"를 설계원칙으로 둔다.**

## 2. 핵심 차별점 (AI 프롬프트 주입)

기존 FM 은 유저가 팀/개인 지시를 UI 위젯(슬라이더·드롭다운·토글)으로 세팅한다. HMB 는 **동일한 전술 의도를 자연어 프롬프트로 선수 에이전트에 주입**하고, LLM 이 선수 성향(멘탈 속성)·상황 맥락과 결합해 이를 전술 인풋으로 해석한다 (`research/tactics-instructions.md` §4).

- **대체(replace)**: 자연어가 UI 위젯을 완전히 갈음. 예: 멘탈리티 7단계 슬라이더 → "오늘은 무리하지 말고 안정적으로, 실점 안 하는 걸 최우선으로 뛰어라".
- **보완(augment)**: 안전이 중요한 항목(오프사이드 트랩 on/off, 역할 프리셋)은 수치 파라미터를 유지하되 자연어로 뉘앙스 추가.
- **심리/팀톡의 우위**: 사기·팀톡·모멘텀은 정형 UI 보다 자연어로 표현할 때 훨씬 풍부하다 (`research/tactics-instructions.md` §3).

핵심 매핑 예시 (전체 14종은 `research/tactics-instructions.md` §4):

| FM 지시 | HMB 자연어 프롬프트 | 방식 |
|---------|---------------------|------|
| Mentality (리스크) | "안정적으로, 실점 최우선" | 대체 |
| Pressing + Trigger | "상대 센터백이 볼 잡으면 즉시 두 명이 압박" | 대체 |
| Mark Specific Player | "상대 10번을 밀착 마크해 지워버려라" | 대체 |
| Offside Trap | "라인 맞춰 올려 오프사이드로 걸어라" | 보완(on/off 플래그 병행) |
| Team Talk / Morale | "침착하게 후반에 뒤집는다는 각오로" | 보완(멘탈 속성 결합) |

## 3. 게임 플로우

한 경기는 "개입 가능 구간(OPEN)"과 "관전 잠금 구간(LOCKED)"이 번갈아 나온다. 유저 인풋 창은 **경기 시작 전**과 **하프타임** 두 번뿐이다 (`research/live-intervention-ux.md` §1).

```
[경기전 셋업] OPEN
  · 상대 팀 분석 리포트 · 포메이션/라인업 확정
  · 선수별 AI 프롬프트 입력(프리셋 칩 + 자유 자연어) · 팀 전술 프리셋
  · 입력 마감 타이머 → [킥오프] 확정
        │ 인풋 freeze → AI 가 시뮬 인풋 사전 생성 → 결정론 시뮬에 주입
        ▼
[전반 진행] LOCKED
  · 시뮬 관전(2D 도트/텍스트 커멘터리) · 실시간 이벤트 로그
  · ✎ "다음 개입 초안" 트레이 — 교체·추가 프롬프트를 미리 작성만(커밋 X)
        │ 전반 종료 휘슬
        ▼
[하프타임] OPEN
  · 전반 요약(핵심 이벤트 3~5) + 히트맵/스탯
  · 선수 교체 · 팀톡/추가 프롬프트(초안 승격) · 개별 지시 갱신
  · 입력 마감 타이머 → [후반 시작] 확정
        │ 갱신 인풋 re-freeze → AI 인풋 갱신 → 엔진 재주입(전반 시드에 연속)
        ▼
[후반 진행] LOCKED  · 관전 · 이벤트 로그 · (이번 경기 커밋 창 없음)
        │ 종료 휘슬
        ▼
[경기 종료] · 결과/스탯 · 프롬프트→결과 인과 리뷰 · 다음 경기 학습 저장
```

**하프타임 루프 원칙** (`research/live-intervention-ux.md` §2 근거): 하프타임은 "팀톡 + 교체 + 전술 조정"이 한 창에 몰리는 고밀도 순간이므로 **정보(전반요약) → 결정(교체) → 지시(프롬프트)** 순서로 시선을 유도해 인지부하·오조작을 방지한다.

## 4. FM 틀 기능 취합

기존 축구 매니지먼트 시뮬(FM)에서 그대로 가져올 기능 목록. 근거는 `research/tactics-instructions.md`.

| 분류 | 취합 기능 | HMB 반영 방식 |
|------|-----------|---------------|
| **멘탈리티** | 7단계 리스크 다이얼(Very Defensive~Very Attacking) | 자연어 프롬프트로 대체(§2) |
| **국면별 팀 지시** | In Possession(템포/폭/패스직접성) · In Transition(역습/카운터프레스) · Out of Possession(압박/수비라인/오프사이드) | 자연어 대체 + 안전 플래그 보완 |
| **역할(Role)** | 포지션별 전문 역할(딥라잉 플레이메이커, 포처, 인버티드 풀백 등) | 역할 프리셋 + 자연어 뉘앙스 보완 |
| **임무(Duty)** | Defend / Support / Attack | 자연어 대체 |
| **개인 지시** | Take More Risks, Roam From Position, Mark Specific Player, Cross More 등 | 자연어 대체 |
| **교체(Substitution)** | 하프타임·경기중 교체(최대 N명) | 하프타임 교체 보드(§9) |
| **팀톡/사기(Morale)** | 경기전/하프타임/경기후 톡, 개인차 적응, 주장/팀리더 | 자연어 프롬프트 + 선수 멘탈 속성 결합 |
| **선수 속성** | 기술/정신/신체 3축 raw attribute | 시뮬 인풋 및 프롬프트 개인화의 기반값 |

> PoC 에서는 이 중 **멘탈리티·국면 지시·역할/임무·개인 지시·하프타임 교체·팀톡**을 우선 취합하고, 스카우팅·이적·재정·훈련 같은 메타게임은 Phase 2(§10).

## 5. AI 주입 아키텍처: 방식1 채택 (확정)

HMB 의 AI 를 어디에 넣을지 두 방식을 비교했고, **방식1을 확정 채택한다.**

- **방식1 (채택)** — 프롬프트 → AI 가 시뮬 **인풋을 사전 생성**(팀/선수별 전술 가중치·계수 + 시드) → 그 인풋으로 **스태틱 결정론 시뮬**을 서버가 실행.
- **방식2 (기각)** — **시뮬 자체가 AI 안에서 돌거나, 매 틱 AI 가 중간 개입**해 행동을 즉석 결정.

| 기준 | 방식1 (채택) | 방식2 (기각) |
|------|------------------------------------------|-------------------------------------|
| **결과 정합성** | 높음 — 시드+인풋 고정 시 "같은 인풋=같은 경기" 보장, 리플레이·부정검증 가능 (`research/match-engine.md` §3) | 낮음 — LLM 비결정성으로 매 실행 결과 발산, 재현 불가 |
| **비용** | 낮음 — AI 호출은 경기당 2회(경기전·하프타임)뿐, 이후 시뮬은 순수 계산 | 높음 — 틱마다 LLM 호출(수만 slice = 대량 토큰) |
| **지연(latency)** | 낮음 — 인풋 생성 후 시뮬은 즉시/배속 재생 | 높음 — 틱마다 추론 대기, 실시간 관전 곤란 |
| **구현 난이도** | 중간 — AI 인풋 스키마 + 결정론 엔진 분리 설계 필요 | 높음 — 실시간 LLM 오케스트레이션 + 상태 동기화 난제 |
| **PvP 적합성** | 높음 — 서버 권위 결정론이라 입력 동기화만으로 PvP 확장 (§11) | 낮음 — 양측 LLM 비결정으로 서버 권위 결정론 불가, PvP 부적합 |

**추천/채택 근거**:
1. 결정론의 관건은 시드이고, 시드를 인풋에 고정하면 "같은 인풋=같은 경기"가 보장되어 리플레이·부정검증이 가능 (`research/match-engine.md` §3). 방식2는 이 정합성을 원천적으로 깬다.
2. 방식2는 매 틱 LLM 호출로 토큰 비용·추론 지연이 폭증. 방식1은 경기당 AI 호출 2회로 억제.
3. Phase 3 PvP 로 가면 서버 권위 결정론이 필수인데, 방식1만 이를 안전하게 만족.

### AI 를 넣는 정확한 지점 (2곳)

방식1 안에서 AI 는 **정확히 두 지점**에만 개입한다 (§3 의 두 OPEN 창과 대응):

- **경기전 인풋 생성**: 유저의 선수별 자연어 프롬프트 + 팀 프리셋 + 라인업 → AI 가 팀/선수별 **전술 가중치 세트(ESMS식 곱셈 계수)** + 초기 시드로 환산.
- **하프타임 인풋 갱신**: 전반 이벤트 요약 + 유저의 추가 프롬프트/교체 → AI 가 **후반용 전술 가중치를 갱신**하고, 전반 시드/상태에 연속되도록 후반 인풋을 재주입.
- 관전(LOCKED) 구간에는 AI 호출이 없다. 초안은 로컬 버퍼에만 저장되고 다음 OPEN 창에서만 커밋된다.

## 6. AI 인풋 스키마 & LLM 연동 (결정)

방식1의 심장은 **"자연어 프롬프트 → 구조화된 전술 인풋"** 변환이다. 이 변환의 정확도·안정성이 게임 정합성의 핵심이므로 스키마와 모델을 명시한다.

### 6-1. `TacticalInput` 스키마 (직렬화 가능 계약)

AI 는 자유 텍스트가 아니라 **고정 스키마 JSON** 을 출력한다(구조적 출력 강제). 이 JSON 이 곧 결정론 엔진의 입력이자 PvP 네트워크 페이로드(§10 경계원칙)다.

```
TacticalInput {
  seed: uint64,                         // 결정론 시드(인풋의 일부로 고정)
  team: {
    mentality: -3..+3,                  // 리스크 스칼라
    tempo: 0..1, width: 0..1,
    lineHeight: 0..1, pressingIntensity: 0..1,
    directness: 0..1, offsideTrap: bool  // 안전 플래그(보완 항목)
  },
  players: [{
    playerId,
    role: enum, duty: defend|support|attack,
    weights: {                          // ESMS식 곱셈 계수 자리
      attack: 0..2, defend: 0..2, press: 0..2,
      risk: 0..2, positioning: 0..2, roam: 0..2
    },
    markTarget?: playerId,              // 전담 마크
    mentalModifier: -1..+1             // 팀톡·사기 반영(멘탈 속성 결합)
  }],
  meta: { generatedAt, promptHash }     // 재현·감사용
}
```

- 계수 범위·enum 은 **엔진이 검증**하고 범위를 벗어나면 클램프(안정성). AI 산출이 스키마 위반이면 1회 재요청 후 프리셋 기본값 폴백.
- 하프타임 갱신은 동일 스키마의 `players[].weights`·`team` 만 델타 적용(시드는 연속).

### 6-2. LLM

- **모델**: **Claude**. 프롬프트→`TacticalInput` 변환에 **tool-use / JSON schema 강제**로 구조적 출력.
- **PoC 티어**: **Claude Sonnet**(비용·지연 균형). 해석이 애매하거나 상대분석이 복잡한 경우에 한해 상위 모델로 에스컬레이션.
- **호출 예산**: 경기당 최대 2회(경기전 1 + 하프타임 1) × 양팀. 캐싱: 동일 프롬프트+선수풀 조합은 결과 캐시.

### 6-3. 밸런스 원칙 — "단일 최적 프롬프트" 방지

프롬프트가 하나의 정답으로 수렴하면 게임성이 죽는다. 이를 막는 설계 규칙:

1. **선수 종속성**: 같은 프롬프트라도 선수의 raw 속성에 따라 `weights` 산출이 달라진다(느린 수비수에게 "높은 라인 압박"은 리스크↑).
2. **상대 맥락 종속성**: 상대 라인업·전술이 AI 프롬프트 해석에 입력되어 "상성"이 생긴다.
3. **소프트 캡 + 시드 노이즈**: 극단 계수는 체력·응집도 페널티. 결정론을 지키되 시드 고정 노이즈로 완전 재현 가능한 분산을 준다.
4. **검증 목표**: PoC 의 핵심 성공 기준은 "서로 다른 프롬프트 전략이 서로 다른, 그러나 납득 가능한 결과를 낸다"이다(§9).

## 7. 매치 엔진 설계 방향

근거: `research/match-engine.md`.

- **모델 선택**: FM식 0.25초 물리 slice 는 결정론 유지·검증 비용이 크다. HMB 는 **ESMS식 "능력치 → 팀 총합(Tackling/Passing/Shooting) → 전술 곱셈 계수 → 확률 이벤트"** 를 채택. 시간 진행은 **분/포제션 단위 이벤트 시뮬**.
- **AI 인풋 접합**: §6 의 `TacticalInput.players[].weights` 가 곧 ESMS 곱셈 계수 자리에 들어간다. "인풋만 바꾸고 시뮬은 고정" 원칙과 정합 (`_synthesis.md` 연결1).
- **결정론/시드**: 확률을 쓰되 **시드를 인풋의 일부로 명시 저장**하고 동일 RNG 강제. FM 처럼 시드를 흔드는 방식은 배제 (§3-3).
- **득점 판정**: 슛 → xG → 시드 고정 Poisson 샘플. heavy-tail 보정 유의.
- **검증/재현**: 초기 시드 + 선택 데이터 + 인풋 로그만 저장하면 headless 재구성으로 경기 재현·비결정 flag 가능 (§9의 PvP-ready 경계 기반).
- **레퍼런스**: **ESMS**(eliben/esms) = 확률·계수 로직, **open-football**(ZOXEXIVO, Rust) = 결정론 아키텍처.

## 8. 렌더링 / 표현 방향

근거: `research/rendering.md`.

- **PoC 권장 = 웹 2D 탑다운 도트 뷰**. 오브젝트 ~23개라 성능 병목 없음. FM 유저 다수도 2D 선호.
- **기술 스택**: 최저비용 = HTML Canvas 직접, 확장 = **PixiJS v8** 또는 Phaser 4 (§11 기술스택과 정합, PixiJS 채택).
- **에셋 원가 ≈ 0**: 도형 + 유니폼 2색 + 번호. **3D 는 리깅·모션캡 에셋이 진짜 비용이라 Backlog**(§10).
- **엔진 출력 접합**: ESMS 는 물리 좌표를 안 내므로 확률 이벤트 로그를 만들고, 렌더 좌표는 경량 보간 레이어로 별도 생성 (`_synthesis.md` 연결3). PoC 는 텍스트 커멘터리 + 최소 도트 이동으로 충분.
- **반응형**: 피치 종횡비 고정 + 스케일, 폰/데스크탑 카메라·HUD 분기, 배속(즉시/1x/2x).
- **앱 래핑**: **Capacitor** — WebView 로 Canvas/WebGL 재사용, 렌더 레이어 재작성 없음.

## 9. 라이브 개입 UX

근거: `research/live-intervention-ux.md`.

- **상태머신(5-상태)**: `PreMatchSetup`(OPEN) → `FirstHalf`(LOCKED) → `HalfTime`(OPEN) → `SecondHalf`(LOCKED) → `FullTime`. 커밋은 OPEN 에서만.
- **엔진 계약**: OPEN 커밋 시 프롬프트 페이로드(선수별 자연어 + 프리셋 태그 + 교체)를 엔진에 주입 + 입력 lock. 타이머 만료 = 확정 버튼과 동등한 freeze. LOCKED 초안은 로컬 버퍼만.
- **개입 이원화**: 무거운 개입(하프타임 자유 프롬프트) + 가벼운 개입(상시 프리셋 칩 8종). 프리셋 = `research/tactics-instructions.md` §5.
- **폰 모드**: "세로 스텝 위저드"(요약→교체→프롬프트 3스텝), 프리셋 칩 우선 + 음성입력(STT), 타이머 상단·CTA 하단 고정, 초안은 하단 시트.
- **데스크탑 모드**: "3분할 대시보드"(좌: 요약/히트맵, 중: 드래그&드롭 교체, 우: 프롬프트 컴포저), 키보드 지향, 관전 중 우측 패널 상시 열림(비활성).
- **하프타임 인지부하 설계**: 정보→결정→지시 스텝 분리(FM 하프타임 교체 버그 이력 교훈).

## 10. 매니지먼트 메타게임 — 덱 수집 + 프리셋 (Phase 2)

PoC 검증 후 **바로 다음 순위**로 붙이는 지속성·수익 레이어. 유저가 선택한 방향은 **"수집 + 프리셋 둘 다"** (FC 온라인형 카드 수집 위에 덱 프리셋 관리).

### 10-1. 선수 카드 수집 (Collection)
- 선수를 **카드/자산**으로 보유. 획득 경로: 팩(랜덤)·마켓(거래)·시즌 보상·스카우팅 산출. (수익모델 후크: 팩/시즌패스 — 세부는 후속 결정)
- 카드 = 선수 + raw 속성(기술/정신/신체) + 성장 상태. **훈련**으로 속성 성장, **재정**으로 이적/영입.
- 보유 풀(로스터)에서 스쿼드를 구성.

### 10-2. 덱(프리셋) 구성 (Preset)
- **덱 = 스쿼드(선발+벤치) + 포메이션 + 팀 전술 프리셋 + 선수별 프롬프트 프리셋 세트**를 하나로 묶어 저장.
- 여러 덱을 저장하고 상대·상황에 따라 **원클릭 전환**(예: "수비 안정 덱", "총공세 덱").
- 경기전 셋업(§3)에서 덱을 불러오면 라인업·프롬프트가 일괄 세팅되어 개입 창 시간을 절약.

### 10-3. 연결 시스템
- **스카우팅**: 상대/시장 선수 분석 → 카드 획득 후보 + 경기전 상대분석 리포트(§3) 소스.
- **이적/재정**: 카드 거래·영입 경제. 예산 관리.
- **훈련**: 카드 속성 성장 → §6 밸런스의 "선수 종속성"에 직접 영향(성장한 선수는 같은 프롬프트로 더 나은 계수).

> Phase 2 는 §6 의 `TacticalInput` 이 이미 `playerId` 기반이라 카드 시스템과 자연스럽게 접합된다(스키마 재설계 불필요).

## 11. 기술 스택 & 결정론 구현 (결정)

- **프론트**: **TypeScript + React**(UI/상태머신) + **PixiJS v8**(2D 피치 렌더). 폰/데스크탑 반응형 분기.
- **서버(권위)**: **TypeScript(Node)** — 매치 엔진·시드 관리·AI 인풋 생성 오케스트레이션을 서버에서 실행. 클라는 결과 재생만.
- **AI 연동**: 서버가 Claude 호출(§6), `TacticalInput` structured output 수신·검증.
- **결정론 구현**: 시드 PRNG(xorshift/mulberry32 류) 강제, **`Math.random` 전면 금지**. 부동소수 비결정 리스크 구간은 정수/고정소수 연산으로 격리. 매치는 `(seed + selectData + inputLog)` 만으로 headless 재현 가능해야 함.
- **모노레포**: `packages/engine`(순수 결정론, 프레임워크 무관) · `packages/server` · `apps/web`. 엔진을 프레임워크에서 분리해야 headless 재현·테스트·향후 Rust 포팅이 가능.
- **후순위 최적화**: 성능 한계 시 `packages/engine` 을 Rust(`open-football` 참고)로 포팅. PoC 는 TS 로 충분.

## 12. Phase 1 — 싱글 PoC 범위

**Phase 1** 은 싱글플레이어(vs AI 감독) **PoC** 로, 핵심 루프(프롬프트→AI 인풋→결정론 시뮬→개입→결과)의 **재미와 기술 성립성**을 검증한다.

### 포함 기능 (In scope)
- 경기 1건 완주 루프: 경기전 셋업 → 전반 → 하프타임 → 후반 → 종료·리뷰.
- 자연어 프롬프트 주입(선수별 자유 입력 + 8종 팀 프리셋 칩) + AI 의 **경기전/하프타임 인풋 생성·갱신**(방식1, §5·§6).
- `TacticalInput` 스키마 + Claude structured output 변환 파이프라인.
- ESMS식 결정론 매치 엔진(분/포제션 단위 확률 이벤트, 시드 고정), 이벤트 로그.
- 2D 탑다운 도트 뷰 + 텍스트 커멘터리(배속), 폰/데스크탑 반응형.
- FM 취합 최소 세트: 멘탈리티·국면 지시·역할/임무·개인 지시·하프타임 교체·팀톡(§4).
- vs AI 감독: 상대 감독 인풋도 동일 파이프라인.
- **밸런스 검증 계측**: 서로 다른 프롬프트 전략이 서로 다른/납득 가능한 결과를 내는지 측정(§6-3).

### 비범위 (Out of scope — PoC 제외)
- **Phase 2 로**: 덱 수집·프리셋, 스카우팅·이적·재정·훈련 (PoC 직후 착수).
- **Phase 3 로**: 실시간 PvP·네트워킹·매치메이킹.
- **Backlog**: 3D 렌더링/모델·모션캡, 리그·토너먼트·랭킹·시즌, 앱스토어 배포(Capacitor 래핑은 웹 검증 후).

### PvP-ready 경계 (설계원칙)

PoC 부터 **PvP-ready 경계**를 지킨다. **Phase 1 싱글 단계에서 시뮬을 서버 권위·결정론·입력 로그 재생 가능하게 만들어, Phase 3 에서 네트워킹만 얹으면 되게 하는 원칙**이다 (`research/match-engine.md` §3, `_synthesis.md` 연결5):

1. **시뮬은 서버(권위)에서 실행** — 클라는 결과 재생만. 싱글에서도 클라 계산 금지.
2. **결정론 + 명시 시드** — 시드를 인풋의 일부로 저장, 동일 RNG 강제.
3. **입력 로그 재생 가능** — `(seed + selectData + inputLog)` headless 재현·부정검증.
4. **AI 인풋 스키마를 네트워크 페이로드로 설계** — §6 `TacticalInput` 을 직렬화 계약으로 정의, Phase 3 에서 그대로 상대에게 동기화.

| Phase | 범위 | 핵심 산출 | 검증 기준 |
|-------|------|-----------|-----------|
| **1. PoC** | 싱글(vs AI) 핵심 루프 | 결정론 엔진 + 프롬프트→`TacticalInput` 파이프라인 + 2D 뷰 + 라이브 개입 | 경기 1건 완주 + 프롬프트 전략별 유의미·납득가능 결과(§6-3) + 100% 재현 |
| **2. 매니지먼트 메타** | 덱 수집+프리셋 · 스카우팅·이적·재정·훈련 | 카드 시스템 + 덱 프리셋 + 경제 루프 | 수집→덱구성→경기 순환이 성립, 리텐션 훅 확인 |
| **3. 실시간 PvP** | 두 감독 실시간 대전 | 서버 권위 시뮬 + 입력 동기화 + 매치메이킹 | 코어 재작성 없이 네트워킹 계층만으로 동작, desync 0 |
| **Backlog** | 3D 렌더링 · 리그/랭킹/시즌 · 앱스토어 배포 | — | Phase 1~3 검증 후 우선순위 재평가 |

### Phase 3 실시간 PvP 고려사항 (미리보기)
- **서버 권위 시뮬**: 서버가 결정론 실행, 양측 클라 재생. 방식1(§5)이 이를 가능케 한 핵심.
- **입력 동기화**: 양측 경기전/하프타임 `TacticalInput` 을 서버가 수집·검증 후 동일 시드로 산출.
- **락스텝 vs 서버시뮬**: HMB 는 "OPEN 창에서만 커밋"하는 턴제성 개입이라 **서버 권위 시뮬**이 자연스럽다. state hash 검증·headless replay 로 desync·부정 탐지.
