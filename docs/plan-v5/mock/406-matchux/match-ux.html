요구 5-1 — "경기중 시간을 초까지 표시"

배경부터. 엔진은 45분짜리 하프를 1350틱(=1350초)으로 돌리고, 표기만 0~90' 로 스케일해서 내보낸다. 그래서 로그·스냅샷에 구워진 분(minute)이 진실이고, 화면이 틱 ÷ 60 으로 분을 직접 만들면 한 화면이 두 시각을 말한다 — 실제로 그렇게 터졌다(#388: 헤더 25' 옆에 로그줄 48', 정확히 2배). 그 사고 이후 규율이 "화면에서 표기 스케일을 다시 유도하지 마라" 이고, 그래서 초 표기를 일부러 버렸다.

안전한 재료가 이미 있다. 뷰어 코어에 clockScaleOf(events, snaps) 가 있고, 이건 스케일을 상수로 적는 게 아니라 로그의 휘슬·스냅샷에서 읽어낸다(half_whistle.minute ÷ (tick÷60)). 즉 화면이 규칙을 새로 만드는 게 아니라 데이터가 말하는 스케일을 그대로 쓰는 것이라 #388 금지 조항에 걸리지 않는다. 지금은 QA 컨트롤(viewer-clock-half*)에만 쓰이고 일반 유저 헤더엔 안 뜬다.
⚠️ 목업을 보면 바로 눈에 띄는 것 — 초가 2씩 뛴다. 엔진 1틱 = 실제 1초인데 표기는 2배 스케일이라 32" → 34" → 36" 으로 짝수만 지나간다. 이건 버그가 아니라 스케일 표기의 구조적 귀결이다. 아래 토글로 보간(1초씩 부드럽게) 을 켜 보고 어느 쪽이 나은지 같이 봐 달라 — 보간은 "화면이 데이터에 없는 값을 만든다"는 대가가 있다.

안건 ① — 초 시계 표기 방식

문제: 초를 보여주려면 표기 스케일(틱→분)을 화면이 알아야 하는데, 그 재유도가 #388 사고의 형태였다. 우회로(clockScaleOf — 데이터에서 읽어낸다)는 있다. 남은 것은 초를 얼마나 크게 보여줄 것인가이고, 그건 되돌리기 쉽지 않은 헤더 정보 위계 결정이다.

A 통합 48'32"

분·초를 한 덩어리로. 시계 축을 하나로 통일한다(분도 유도 스케일에서 나온다).
+ 축이 하나라 어긋날 곳이 없고 QA 도구·장면 목록과 표기가 같다.
− #388 이 지킨 "분은 구운 minute" 을 버린다. 헤더 폭도 가장 넓다(폰에서 팀명 잘림 압박).

B 분 크게 + 초 작게 (권장)

분은 지금 그대로 구운 minute, 초만 clockScaleOf 로 붙인다. 시각적으로도 분이 주, 초가 보조.
+ #388 규율을 안 건드린다(분 축 불변) → 기존 계약 8건이 그대로 산다. 폭 증가도 최소.
− 분 경계에서 초가 59"인데 분이 이미 넘어간 1틱 어긋남이 이론상 가능 → 초를 분에 앵커해야 한다(구현 조건).

C 라이브만 초

진행 중엔 48'32", 종료·결과 화면은 90'. 초를 "살아있음의 신호"로만 쓴다.
+ 라이브 체감이 가장 크고 결과 화면은 깔끔.
− 상태에 따라 헤더 모양이 바뀐다 = 유저가 두 형태를 학습해야 한다. 돌려보기에서 "몇 초 장면"을 못 말해 요구의 절반만 충족.
권장 = B. 요구("초까지 보이게")를 충족하면서 #388 이 세운 "분의 축은 구운 minute 하나" 를 유지하는 유일한 안이다. 초 보간은 끄는 쪽을 권장한다 — 데이터에 없는 값을 화면이 만들면 그게 다음 #388 이 된다(짝수 초로 뛰는 건 실제 엔진 해상도의 정직한 표현이다).

요구 5-2 — "선택한 선수가 누군지 피치에서 보이게(내 선수 · 상대 선수 둘 다)"

피치 위 토큰을 눌러 보라. 링이 붙고 옆(폰에선 아래)에 정보 카드가 뜬다. 내 선수는 프롬프트 입력까지, 상대 선수는 정보 열람만. 코어에는 지금 "선택"이라는 개념 자체가 없어서 신설하는 영역이다.

같은 화면에서 겹침을 확인할 수 있게 해 뒀다. 홈 9번은 볼 소유자(노란 링 #fde047, 반경 R+2), 어웨이 4번은 경고 카드 마커(반경 R+6 + 카드 아이콘)를 달고 있다. 선택 링이 이 둘과 안 싸우는지 눌러서 봐 달라. (목업의 선택 링은 R+9 바깥에 그린다.)
⚠️ 실데이터의 함정 — 홈 7번과 어웨이 7번은 같은 playerId(P077)다. 유저 덱과 봇 로스터가 같은 선수 카탈로그를 공유해서 라이브 하프의 상당수가 이 상태다(#324). 아래 체크박스로 "단독 id 키"를 켜고 7번을 눌러 보면 반대 팀이 같이 켜진다 — 이게 구현에서 반드시 skinKeyOf(team, playerId) 로 키를 잡아야 하는 이유다.

안건 ② — 선택 링 스타일

문제: 토큰 주변엔 이미 신호가 둘 있다 — 볼 소유자 노란 링(R+2)과 카드 마커(R+6, 노랑/빨강). 여기에 선택 링을 더하면 세 겹이 되고, 셋 다 켜진 선수에서 무엇이 무엇인지 못 읽으면 신호가 오히려 줄어든다. 게다가 web 의 픽셀 계약 3종(p218-legend-arena·p285-icon-policy·p3-char-skin)이 토큰 주변 픽셀을 재고 있어, 무엇을 그리든 그 계약이 먼저 깨진다(= 어느 안이든 계약 갱신 비용은 동일하다).

A 펄스 링 (권장)

R+9 에 링 하나. 반경·투명도가 천천히 맥동한다. 정지 화면에서도 보이고 움직여서 눈에 띈다.
+ 소유자 링(R+2)·카드 마커(R+6)와 반경이 갈려 세 겹이어도 층이 읽힌다. 구현·계약이 가장 단순.
− 맥동이 계속 돌아 캔버스가 매 프레임 다시 그려진다(이미 rAF 루프라 실비용은 작다).

B 파선 링(회전)

점선 링이 천천히 회전. "선택 도구"라는 관용 표현이라 의미가 즉시 읽힌다.
+ 노란 실선(소유자)과 선 종류로 갈려서 색이 겹쳐도 구분된다.
− 32px 토큰에서 점선은 조각이 3~4개뿐이라 폰에서 거의 실선처럼 보인다(목업에서 폰 폭으로 확인해 보라).

C 발밑 스포트라이트

토큰 아래 타원 글로우. 링을 안 쓰니 위쪽 신호(카드 아이콘)와 절대 안 겹친다.
+ 겹침 위험이 구조적으로 0. 축구 중계 톤에도 맞는다.
− 잔디 위 저채도 글로우라 대비가 가장 약하다. 선수가 몰린 구역에서 옆 선수의 것으로 보인다.
권장 = A(펄스 링). 세 신호를 반경으로 층지게 나누는 것이 가장 확실하고, 계약도 "선택 링 반경 > 카드 마커 반경"이라는 검사 가능한 성질로 박을 수 있다. 내 선수/상대 구분은 링 스타일이 아니라 색+굵기+이름표로 한다(위 표) — 스타일 축과 소유 축을 섞지 않는다.

과거 전용 시크바

요구 5-3 — "동영상 바처럼 보이되 미래로는 못 가고 과거만"

실제로 드래그된다. 라이브 바에서는 빨간 [현재] 선을 넘어가려 해도 막힌다. 뒤로 끌면 과거 보는 중 배지와 [현재로] 버튼이 뜬다. 종료 후 바는 같은 모양이지만 전 구간 자유다.

규칙은 이미 코드에 있다 — UI 가 안 쓰고 있을 뿐이다. clampSeek(target, live, active, MS_PER_TICK)(packages/shared)가 뒤로 자유 · 앞으로 liveTick + grace 제한을 이미 구현해 뒀고 250ms 복구 루프만 이걸 쓴다. 유저가 만지는 슬라이더는 클램프를 안 거치는 raw 호출이라 지금은 미래로도 끌린다. 또 라이브 슬라이더의 max 가 snapCount-1(하프 전체)이라 바의 오른쪽 끝이 곧 스포일러다.
⚠️ 라이브는 서버 권위 시계 위에서 돈다. 250ms 마다 도는 복구 루프가 재생 위치를 서버가 말하는 지점(liveTick)으로 끌어당긴다 — 지금은 화면이 뜰 때마다 jumpToTick(liveTick); play() 를 하고, 표류(drift)가 스냅샷의 12% 를 넘으면 점프해서 따라붙는다. 그래서 "유저가 과거를 보는 중"이라는 모드 플래그가 없으면, 뒤로 끌어 놓아도 0.25초 뒤에 현재로 튕겨 온다. 아래 안건 ③ 은 그 모드에서 어떻게 빠져나오냐를 묻는 것이다.

안건 ③ — 과거에서 현재로 돌아오는 방법

문제: 유저가 뒤로 끌어 장면을 다시 보는 동안, 라이브 경기는 계속 흐른다. "과거 보는 중" 상태를 언제 끝낼 것인가를 정해야 한다 — 복구 루프(250ms)가 헤드를 끌어당기고 있어서 이 규칙이 없으면 유저가 과거를 붙잡고 있을 수 없다. 반대로 영영 안 돌아오면 라이브를 놓친다.

A N초 뒤 자동 복귀

마지막 조작에서 8초(예시) 지나면 스르륵 현재로. 위 체크박스로 켜서 체험할 수 있다.
+ 유저가 아무것도 안 해도 라이브로 돌아온다 — "따라가고 있다"가 기본값.
− 골 장면을 두 번 보려던 유저의 화면이 스스로 도망간다. 타이머 값이 취향 문제라 계약으로 굳히기도 애매하다.

B 수동 [현재로]만 (권장)

뒤로 끌면 배지 + [현재로] 버튼. 유저가 누를 때까지 그 자리에 머문다. 헤드가 liveTick 에 닿으면 자동으로 라이브 모드 복귀.
+ 화면이 유저 의사 없이 움직이지 않는다. 복구 루프는 "라이브 모드일 때만" 도는 한 조건으로 끝난다.
− [현재로]를 못 본 유저는 과거에 머문 채 경기가 끝날 수 있다 → 헤더의 LIVE 배지가 꺼지는 것으로 상태를 계속 말해 줘야 한다.

C 하이브리드 — 자동 복귀 + 취소

A 처럼 자동으로 돌아가되, 복귀 직전 3초 카운트다운을 띄우고 누르면 취소.
+ 두 장점을 다 갖는다.
− 상태가 셋(라이브 · 과거 · 복귀 예고)이 되고, 카운트다운 UI 가 무대 위에 하나 더 올라간다. 지금 크기의 요구에 비해 과하다.
권장 = B(수동만). 이 기능의 목적이 "방금 그 장면 다시 보기"라서, 자동 복귀는 그 목적과 정면으로 싸운다. 라이브를 놓치는 위험은 LIVE 배지 소등 + [현재로] 상시 노출로 충분히 말할 수 있다. (A 를 고르면 타이머 값이 튜닝 대상이 되므로 EngineConfig 가 아닌 web 상수로 어디에 둘지도 같이 정해야 한다.)

      행동 가시화 이펙트

      요구 4-2 — "지금 무슨 상황인지 보이게 · 팀별 색으로 어느 팀 행동인지"

      버튼을 눌러 재생해 보라. 반복 루프를 켜면 네 이펙트가 순환한다. 색은 전부 뷰어 코어의 teamRgb(side) 를 그대로 쓴다 — 홈 파랑 #3b82f6 / 어웨이 빨강 #ef4444.

      제안 캔버스 데모
      이펙트는 전부 이미 로그에 실려 오는 이벤트로만 만들었다 — 엔진 무접촉.
      현행 같은 4개 이벤트의 현재 상태
      행동엔진 이벤트지금 화면
      공 잡음(수신)pass확산 링(팀색) — "떠났다"로 읽힌다
      패스 실패interception확산 링 + 점(팀색) — 수신과 모양이 거의 같다
      걷어내기clearance아무것도 없음 — 캔버스·토스트·HUD·로그 전부 0
      태클 성공tackle무채색 토스트 TACKLE(#cbd5e1) — 어느 팀인지 모른다
      1순위는 걷어내기다 — 엔진이 팀·선수를 다 주는데 화면 표현이 하나도 없다. 경기당 팀별 약 16회 발생한다. (그리고 텍스트 타임라인에는 이미 경기당 ~32건이 폴백 문구로 노출 중이다 → #325)
      행동제안하는 시각 문법왜 이 모양인가
      공 잡음수축하는 링(밖→안) + 토큰 밝기 플래시현행 확산 링과 방향을 반대로 둬서 "받았다 / 보냈다"가 방향으로 갈린다. 색·굵기를 안 바꾸고 방향만 뒤집는 최소 변경.
      가로챔확산 링 + X 슬래시 + 토스트 가로챔!패스 계열과 링 모양이 같아 못 갈렸다. 슬래시가 "끊었다"를 말한다.
      걷어내기쐐기(삼각) 궤적 + 속도선 3줄 + 토스트 걷어냄!방향성이 본질인 행동(위험지역 밖으로)이라 링이 아니라 벡터로 그린다. 패스와 헷갈리지 않는다.
      태클 성공방사 스파크 + 팀색 토스트모양은 그대로 두고 색만 팀색으로. 요구("어느 팀 행동인지")를 가장 싸게 충족한다.
      ⚠️ 요구 4-2 의 4개 중 2개는 지금 만들 수 없다. 태클 miss 와 제껴짐은 사실 같은 사건인데, 엔진이 태클을 성공했을 때만 로그에 push 한다(contest.ts). 실패는 내부 observer 에만 있고 MatchLog 에 안 실린다. dribble 액션도 이벤트가 0건이다. 즉 화면이 아무리 잘 그려도 그릴 데이터가 없다.

      안건 ⑤ — 태클 miss · 제껴짐을 어떻게 할 것인가

      문제: 이 에픽은 엔진 시뮬 로직 무접촉이 전제다(엔진은 QA 트랙 #25 / E4 소유). 그런데 요구 4-2 가 지목한 4개 중 2개는 엔진이 이벤트를 안 만들어서 뷰어가 알 방법이 없다.

      A 엔진 이벤트 추가 요청 (권장)

      tackle:miss · dribble:past 2건을 #407 / QA #25 에 레이즈하고, 이번 에픽은 가능한 4개(수신·가로챔·걷어내기·태클성공)를 먼저 낸다.
      + 이벤트가 진실이라 로그·통계·리플레이가 전부 같은 사실을 말한다. 결정론 재현 계약도 깨지지 않는다(이벤트 추가는 로그 스키마 additive).
      − 엔진 트랙 일정에 의존한다 → 요구 4-2 가 두 번에 나눠 완성된다.

      B 뷰어가 스냅샷으로 추론

      틱 사이 소유 변화·거리 변화를 보고 "태클이 실패했나 보다"를 추측해서 그린다. 선례 = 지금 SURGE! 가 그렇게 만들어진다.
      + 엔진 없이 이번 에픽 안에서 4개를 다 낸다.
      − 이건 이벤트가 아니라 추측이다. 로그·통계에는 없고 화면에만 있는 사실이 생겨, "화면엔 태클 실패가 떴는데 로그엔 없다"가 정상 상태가 된다. 엔진 튜닝이 바뀌면 추론식이 조용히 어긋나고, 그 어긋남을 잡을 계약을 세울 수가 없다(정답이 없으므로).
      권장 = A. HMB 는 "보이는 것 = 데이터" 를 규율로 세워 온 프로젝트고(§2-2 인지 갭), B 는 그 규율에 정면으로 반한다. 지금 미시각화 1순위인 걷어내기만 해도 체감이 크게 오르므로, 4개를 먼저 내고 2개는 엔진 이벤트가 오면 같은 문법으로 얹는다.
