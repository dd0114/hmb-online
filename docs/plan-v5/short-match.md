> 시간 표기는 축구 시간처럼 0~90으로 가지만 절대 시간은 3분으로 끝나게."*

| 축 | 지금 | 바꾼 뒤 |

## 1. 왜 "재생 속도만"으로는 안 되나 — 되짚기

3분 하프를 만드는 방법은 두 가지뿐이다.

1. **틱 수를 줄인다**(경기 자체를 짧게) — `matchMinutes`.
2. **같은 틱을 더 빨리 재생한다** — 배속.

②만으로 3분을 만들려면 지금의 **2.3배속**이 필요하다(411s → 180s). 그 그림은 **이미 hero 가 눈으로
보고 기각했다**(#221 2026-07-28: A=40분 엔진 vs B=크루즈 20x 를 실제 뷰어로 만들어 비교 → *"A 쪽
체감이 낫다"*). 그래서 이 설계는 **①이 주(主)이고 ②는 hero 가 지정한 1.2배**다.

배속 1.2 는 그 위에서 두 가지 일을 한다: 화면 움직임이 20% 빨라지고(hero 요구), 같은 3분 창에
**10% 더 많은 경기 내용**이 들어간다(45분 vs 40분).

## 2. 축별 설계

### 2.1 게임 길이 — `matchMinutes: 45` (엔진)

45 를 고른 근거는 둘이다.

- **3분에 가장 가깝다.** 실측(20시드 × 2하프 = 40하프, 배속 1.2 적용):

  | matchMinutes | 하프틱 | min | p50 | mean | max |
  |---|---|---|---|---|---|
  | 40 | 1200 | 141.7 | 162.6 | 161.1 | 185.8 |
  | 44 | 1320 | 151.4 | 175.9 | 176.5 | 208.5 |
  | **45** | **1350** | **154.9** | **176.6** | **178.7** | **211.7** |
  | 48 | 1440 | 169.6 | 188.9 | 188.9 | 217.3 |
  | 52 | 1560 | 182.3 | 204.9 | 205.3 | 234.9 |

- **표기 스케일이 정확히 2 가 된다**(90/45). 즉 **표기 1분 = 30틱**으로 딱 떨어진다. 44 였다면
  2.0454… 라 같은 3분을 얻으면서 나머지만 지저분해진다.

재현: `MM=44,45 MUL=1,1.2 npx tsx <sweep>` (측정 스크립트는 `tools/measure-playback-pace.mjs` 와
같은 모델 = `viewer-core/playback.mjs` 의 `autoPaceDurationMs`).

### 2.2 배속 1.2 — 코어 `PACE` 상수 한 곳 (viewer-core)

`PACE.TICKS_PER_SEC: 2 → 2.4`.

- **왜 코어인가**: `PACE` 는 렌더 루프와 재생 길이 모델(`autoPaceDurationMs`)이 **같이 읽는 SoT**다
  (#216). 여기에 넣으면 서버 창 정합 가드(`tools/pace-config.test.ts`)가 **자동으로 새 값을 재유도**한다.
  web 쪽 배율(`live-pace.paceRate`)에 1.2 를 넣으면 그 가드는 여전히 1.0x 길이를 재서 창과 어긋난 채
  green 이 되고, **다시보기(VOD)·QA 뷰어·standalone 은 배속이 안 걸린다**(라이브만 빨라진다).
- **홀드는 배속 대상이 아니다** — 골 정지·파울 홀드(`FOUL_HOLD_MS`)·데드볼 자막
  (`DEADBALL_PAUSE_MS`)은 *읽는 시간*이다. 그래서 실효 단축은 1.2배가 아니라 그보다 조금 작다
  (측정에 이미 반영돼 있다: 45분 1.0x p50 208.8 → 1.2x p50 176.6 = ×0.846).

### 2.3 표기 0~90 — 엔진 `tickToMinute` 에 표기 스케일

```
displayMinutes(신규 config, 기본 90) / matchMinutes(45) = 2
tickToMinute(tick) = floor(tick * msPerTick / 60000 * scale)     // = floor(tick / 30)
```

- 하프 휘슬 1350틱 → **45'**, 종료 2700틱 → **90'**. 표기 1분이 30틱마다 올라간다(건너뛰는 값 없음).
- **왜 엔진인가**(표시 계층이 아니라): `minute` 은 `TickSnapshot`·`MatchEvent` 에 **구워져 로그에
  실린다**. 소비자는 뷰어 시계·`viewer-core/log-lines`·web `LogPanel`·타임라인 핀 넷인데 전부 그
  구워진 값을 읽는다 → **엔진 한 줄이면 전 화면이 따라온다**. 표시 계층에서 곱하면 네 곳에 같은
  규칙이 복제되고, 새 소비자가 생길 때마다 조용히 빠진다.
- **구 로그 호환이 공짜다**: 과거 경기 로그의 `minute` 은 그때 값(90분 경기의 0~90)이 그대로 박혀
  있으므로 다시보기가 안 깨진다. `MatchLog` 스키마에는 `configVersion`(문자열)만 실리고 config
  전체가 실리지 않으므로, 소비자가 스케일을 되계산할 일 자체가 없다.
- ⚠️ **`full_whistle` 은 `minute: config.matchMinutes` 를 직접 쓴다**(`match.ts`). 같이 고치지 않으면
  다른 이벤트는 0~90 인데 **종료 휘슬만 45'** 로 뜬다.
- 다른 곳에서 분을 파생하지 않는다 — `grep 60000` 전 리포 결과 `match.ts:158` 한 줄뿐이다.

### 2.4 서버 시계 (`server-java`)

- `hmb.match.clock.half-real-ms: 420000 → 180000` (+ `MatchClockProperties.halfRealMs` 기본값).
- 창 대비 필요 배율(`live-pace.paceRate`) = 실측 155~212s / 180s = **0.86 ~ 1.18** →
  컨트롤러 범위 [0.6, 1.6] 안. 여유가 충분하다(#221 이 40분+150s 에서 경고한 상한 물림과 다른 지점).
- `tools/pace-config.test.ts` 는 **엔진으로 직접 재서 yml 과 ±20% 대조**하므로 자동 재유도된다.
  단, 그 안의 `snapshots.length > 2000`(하프가 리얼 config 인지 확인하는 안전장치)은 **1350틱 기준으로
  같이 옮긴다** — 안 옮기면 이 가드가 먼저 빨간다.
- `MatchClockFlowTest`·`MatchAutoModeTest` 는 값을 **테스트가 주입**하므로 영향 없다.
- 감독시간(`halftime-ms`) = **hero 게이트**(§4).

### 2.5 리얼리즘 밴드 재설정 (엔진)

45분 경기의 실측(20시드, engine@0.28.0 main 기준):

| 지표 | 90분(현행) | **45분** | 비고 |
|---|---|---|---|
| 골/경기 | 5.75 | **2.90** | ×0.50 |
| 슛/팀 | 12.35 | **7.78** | **×0.63 — 반이 아니다** |
| 유효슛/팀 | 5.33 | 3.10 | ×0.58 |
| 슛당 xG | 0.220 | 0.200 | 비율 지표 — 유지 |
| 슛→골 전환% | 23.5 | 18.9 | |
| 패스 성공% | 82.7 | 82.5 | 비율 지표 — 유지 |
| 코너/팀 | 4.08 | 2.42 | |
| 스로인/팀 | 17.45 | 9.35 | |
| 팀 폭 m | 48.5 | 48.3 | 비율 지표 — 유지 |

⚠️ **볼륨 지표를 "×2 환산"으로 밴드에 재사용하면 안 된다.** 실측이 선형이 아니다 —
경기를 4등분한 슛 밀도가 **5.30 / 2.23 / 2.55 / 2.27**(팀당, 90분)로 **초반이 후반의 2.3배**다.
짧은 경기는 그 초반 구간의 비중이 커져 단위시간 밀도가 올라간다(45분 4등분 = 3.52 / 1.77 / 1.35 / 1.13).
→ 밴드는 **45분에서 새로 뜬다**(비율 지표는 그대로 유지).

⚠️ **밴드를 뜨는 시점 = engdeep #358(파울 복구) 착지 후.** 지금 main(0.28.0)은 파울이 팀당 2.13
(구 밴드 10–14)로 이미 밖이고 #358 이 그걸 되돌리는 중이다. 이 상태에서 밴드를 뜨면 **#358 이 그
밴드를 깬다**. 그래서 밴드 재도출은 이 에픽의 **마지막 웨이브**다.

### 2.6 리플레이·재개 호환

- `config.version` **범프 필수**(경기 길이 = 재현 계약). 그 순간 진행 중 매치의 `resumeState` 가
  버전 불일치로 거부된다 → **배포 시점에 하프타임/GEN2 에 있던 매치는 후반을 못 돌린다**
  (#221 이 이미 적어둔 주의. 회수 경로 = `POST /api/matches/{id}/abandon`, #217).
  배포 전 진행 중 매치를 비우거나 테스터에게 고지한다.
- **끝난 경기 다시보기는 안 깨진다**(§2.3).

## 4. hero 게이트 (게임 내용 — 이 창에서 확인)

### Q1. 감독시간 180초를 유지하나?

하프가 3분이 되면 감독시간(3분)이 하프와 같아진다 — 총 9분 중 3분이 지시 화면이다.

- **유지 권장.** 감독시간은 "하프 길이의 비율"이 아니라 **글을 쓰는 시간**이고, #216 에서 60→180 으로
  올린 이유가 그것이다. 그리고 하프타임 지시 생성이 실측 **57.7s(effort low) ~ 121s(full)** 라
  창을 120초 아래로 내리면 **지시가 반영되기 전에 후반이 시작될** 위험이 있다.
  급한 유저에게는 이미 **오토 모드(#249)** 라는 탈출구가 있다(감독시간 통째로 건너뜀).
- 대안: 120초 / 90초.

### Q2. 3분 하프 경기의 골 밀도

지금 **"경기당 5골"은 hero 가 정한 목표**이고 `shot-frequency.test.ts` 한 줄이 그 SoT 다. 경기를 반으로
줄이면 **아무것도 재튜닝하지 않아도 2.90골/경기**가 된다 — 즉 가만두면 그 결정이 **부작용으로** 뒤집힌다.

- **A) 짧은 축구 그대로 (권장)** — 골 2.90/경기 · 슛 7.78/팀. 재튜닝 0.
  ⚠️ **보는 시간당 골은 오히려 늘어난다**: 5.75골/14분관전 = 0.41 → 2.90골/6분관전 = **0.48/분**.
  "골이 줄어든다"는 건 경기 기록지 얘기지 관전 체감이 아니다.
- **B) 경기당 5골 유지** — `chain.goalValue` 상향 재보정 1회. 3분 하프에 골 2.5개 = **36초에 한 골**.
  대가: 슛도 같이 올라간다(0.15.0~0.19.0 이 "슛 남발이 관전을 해친다"고 깎은 축을 되살린다).
