## 0. 한 줄 요약

경기 시작 · 전반 종료 · 후반 시작 · 경기 종료 네 지점에 **브릿지**를 넣되, 스킵 모드(#421)의 하프
리포트와 **같은 하나의 흐름 상태머신** 위에 얹는다. 브릿지는 **패널 라우팅을 바꾸지 않는다** —
`panelForState` 는 한 글자도 안 건드리고, 브릿지는 그 위에 뜨는 **오버레이**(종료형 2개)이거나
**이미 있는 대기 화면의 승격**(대기형 2개)이다.

핵심 결정 세 줄:

1. **브릿지는 상태가 아니라 _전이_ 에 붙는다.** 열림은 전이가 정하고, **내용은 현재 상태가 정한다** —
   그래서 브릿지가 낡아 거짓말하는 상태가 구조적으로 생기지 않는다.
2. **스킵 리포트는 브릿지의 앞 카드다**(별도 레이어 아님). 하나의 카드 스택, 하나의 닫기.
3. **오버레이 소유자는 `MatchPage`** 다(`StageShell` 아님) — #421 이 남긴 D6 갭이 여기서 닫힌다.

## 1. 왜 하나로 통합해야 하나 (문제 정의)

#421 W2 는 스킵 성공 시 **하프 리포트 팝업**(공지형 카드 스택)을 띄운다. #424 는 같은 순간에
**전반 종료 브릿지**("전반이 끝났습니다 / 다음은 감독시간")를 요구한다. 둘을 따로 만들면:

- 전반을 스킵한 유저는 **팝업 두 개**를 연달아 닫는다(리포트 → 브릿지). 어느 쪽이 위인지, 어느 쪽을
  닫아야 다음으로 가는지가 매번 z-index 싸움이 된다.
- 스킵하지 않은 유저는 브릿지만, 스킵한 유저는 리포트만 보는 **불균질한 흐름**이 되기 쉽다.
- 트리거 소스가 둘(스킵 응답 / 서버 전이 관측)이라 **중복 발화**가 난다 — 스킵 응답이 캐시를
  갱신하면 전이 관측도 같이 발화하므로, 통합하지 않으면 리포트와 브릿지가 각자 한 번씩 뜬다.

그래서 **흐름 오버레이는 하나**이고, 리포트와 브릿지는 그 안의 **카드**다.

## 2. 현행 상태머신 (변경하지 않는 것)

### 2.1 서버 상태와 전이 (SoT = server-java)

```
BRIEFING ──[유저: 킥오프]──▶ GEN1 ──[잡 완료]──▶ FIRST_HALF
   └ phase_ends_at 없음            └ 없음            └ 창 = playbackMs(폴백 220s)

FIRST_HALF ──[창 만료 | POST /skip]──▶ HALFTIME ──[유저: 후반시작 | 만료]──▶ GEN2 ──[시뮬]──▶ SECOND_HALF
                                        └ 창 = halftimeMs(180s, 오토면 0)                        └ 창 = playbackMs

SECOND_HALF ──[창 만료 | POST /skip]──▶ FINISHED (+정산)
```

- 전이 트리거는 **셋**: 스위퍼 1초(`MatchClockSweeper`) · 조회 lazy(`advanceDueForRead`) · 유저 액션
  (`POST /kickoff`·`/resume`·**`/skip`**). 어느 쪽이 먼저 밟아도 결과는 같다(전부 CAS).
- **오토 모드(#249)**: 서버가 감독시간을 0초로 열고 같은 스윕에서 `SECOND_HALF` 까지 잇는다.
  → `FIRST_HALF` 다음 관측 상태가 `HALFTIME` 이 아니라 `GEN2`/`SECOND_HALF` 일 수 있다.
- **`POST /skip`(#421 W1)**: `phase_ends_at` 을 now 로 **당기기만** 한다. 되감기 불가
  (`AND phase_ends_at > :now`) — 즉 **브릿지가 서버 시계를 멈추거나 늦출 수 있는 수단은 없다.**
  이 사실이 §4 의 "끝맺음 = 버튼인가 자동인가" 판정의 근거다.

### 2.2 클라 패널 라우팅 (무편집)

`MatchPage` → `panelForState(state)`(`match-logic.ts:30`):

| state | panel | 화면 |
|---|---|---|
| `BRIEFING` | `briefing` | `BriefingPanel` (Layout) |
| `GEN1` · `GEN2` | `genwait` | **`GenWaitPanel`** (Layout) |
| `FIRST_HALF` · `SECOND_HALF` | `live` | `StageShell` |
| `HALFTIME`(`H1_BREAK`) | `halftime` | `StageShell`(감독 탭) |
| `FINISHED` | `result` | `StageShell`(결과 탭) |
| `FAILED`/`ABANDONED`/기타 | … | 각 폴백 |

⚠️ **`panelForState`·`statePanelFor`·`tabsFor`·`sheetHeight` 는 한 줄도 고치지 않는다.** 브릿지를
패널로 만들면 `#348`/`#355` 의 시트 높이 등급, `#284` 의 탭 규칙, `#244` 의 감독시간 레이아웃이
전부 사정권에 들어온다. 브릿지는 **그 위에 뜨는 층**이거나 **이미 있는 패널의 내용 보강**이다.

### 3.2 카드 스택 구성 — 스킵 여부에 따라 앞에 리포트가 붙는다

```
전반 종료(스킵 안 함)  :  [ B2 브릿지 ]                                    ← 1장
전반 종료(스킵함)      :  [ 전반 리포트 ][ 주요 인물 ][ B2 브릿지 ]          ← 3장 (평점 모듈 없으면 2장)
경기 종료(스킵 안 함)  :  [ B4 브릿지 ]
경기 종료(스킵함)      :  [ 후반 리포트 ][ 주요 인물 ][ B4 브릿지 ]
```

- **브릿지 카드가 언제나 마지막**이다 = "무슨 일이 있었나 → 이제 뭐가 오나" 순서이고,
  **마지막 장의 CTA 가 곧 끝맺음 포인트**다. #421 의 "닫으면 바로 후반"이 그대로 성립한다.
- 카드 순서·구성은 **배열 한 줄**이라 조정 포인트(§8-3)다.

## 4. 지점별 확정표 (요구 ①②)

| | **B1 경기 시작** | **B2 전반 종료** | **B3 후반 시작** | **B4 경기 종료** |
|---|---|---|---|---|
| **트리거 전이** | `BRIEFING → GEN1` | `FIRST_HALF → (HALFTIME\|H1_BREAK\|GEN2\|SECOND_HALF)` | `HALFTIME\|H1_BREAK → GEN2` | `(SECOND_HALF\|GEN2\|HALFTIME\|H1_BREAK\|FIRST_HALF\|GEN1\|BRIEFING) → FINISHED` |
| **트리거 주체** | 유저(킥오프 버튼) | 서버 창 만료 **또는** `POST /skip` | 유저([후반 시작]) **또는** 만료 | 서버 창 만료 **또는** `POST /skip` |
| **형태** | 패널 승격(`GenWaitPanel`) | 오버레이 카드 | 패널 승격(`GenWaitPanel`) | 오버레이 카드 |
| **"지금/다음" 설명** | `FlowStepper`(브리핑✓ → **전반 준비** → 전반 → …) + 기존 정경 문구 | 카드 본문 = 현재 상태 파생 | `FlowStepper`(… 감독시간✓ → **후반 준비** → 후반 → 결과) | 카드 본문 + `다음: 경기 보상과 결과` |
| **끝맺음** | **자동** — `GEN1→FIRST_HALF` 전이 + **킥오프 비트①**(1.2s) | **유저 버튼** | **자동** — `GEN2→SECOND_HALF` + **킥오프 비트②** | **유저 버튼** |
| **닫으면 어디로** | 전반 라이브(`StageShell`) | 현재 상태의 패널(감독시간/후반/…) | 후반 라이브 | 미확인 봉투가 있으면 **#405 보상 시트**, 없으면 결과 탭 |

> ⚠️ **W5·W6 에서 위 표가 넓어졌다 — 이 문단이 그 이유의 SoT 다.** 원 설계는 트리거를 `X → Y` 단일
> 전이로 적었다. 구현이 배열이 된 것은 규칙이 바뀌어서가 아니라, **클라가 서버 전이를 전부
> 관측하지는 못한다**는 사실을 뒤늦게 반영했기 때문이다. 규칙은 그대로다 —
> *"브릿지는 전이에 붙는다"* + *"관측을 건너뛴 전이도 그 전이다"*.
> - **B2 의 `to` 가 넷**: 오토 모드(#249)가 감독시간을 0초로 열고 같은 스윕에서 후반까지 이어서,
>   `FIRST_HALF` 다음 관측 상태가 `HALFTIME` 이 아닐 수 있다. 빼면 오토 유저는 B2 를 영영 못 본다.
> - **B4 의 `from` 이 일곱**: `FINISHED` 로 들어오는 문이 하나가 아니다. ①시계 롤백에서
>   `enterSecondHalf` 가 `finishMatch(…, S_GEN2)` 를 태우면 관측은 `GEN2 → FINISHED` 다(독립검증 N3)
>   ②탭이 백그라운드면 React Query 가 폴링을 멈춰 중간 상태를 통째로 못 보고 마지막 관측
>   (`FIRST_HALF`·`HALFTIME`·`GEN1`·`BRIEFING`)에서 곧바로 `FINISHED` 가 관측된다.
>   빼면 그 경로에서 **AC4 의 네 번째 지점이 소실**된다.
>
> ⚠️ **한때 `BRIEFING`·`GEN1` 만 제외했고 근거가 거짓이었다**(W6 정정). 코드 주석은 *"거기서
> `FINISHED` 로 가는 전이는 실재한다 — 상대가 브리핑에서 무른 **몰수**(0:0)"* 라고 적었지만,
> 서버 실측은 그 반대다:
> - `state='FINISHED'` 를 쓰는 곳은 `MatchOrchestrator.java:786,793`(둘 다 `finishMatch`) **뿐**이고
>   그 `fromState` 는 `GEN2` 또는 `SECOND_HALF` **뿐**이다.
> - **몰수·포기는 `ABANDONED`** 로 간다(`MatchLockService.java:246,310`) — `FINISHED` 가 아니다.
>
> ⇒ 즉 `BRIEFING`/`GEN1 → FINISHED` 의 유일한 발생 경로도 **관측 누락**이라 위 ②와 같은 부류다.
> 그리고 `90분이 끝났습니다` 가 참인 근거는 `from` 이 아니라 **도착 상태**다 — `FINISHED` 는
> 두 하프 시뮬을 마쳐야만 도달하므로 문구의 참을 상태가 보증한다(§4.4 P7). 재생할 하프가 없는
> 몰수는 `to: ["FINISHED"]` 가 이미 막는다.

### 4.1 왜 B1·B3 은 자동인가 (서버 권위 시계와의 정합)

> ⚠️ 프롬프트 경고 그대로: *"서버가 아직 다음 페이즈를 안 열었는데 브릿지를 닫으면 갈 곳이 없다."*

- `GEN1`/`GEN2` 는 **다음 페이즈가 아직 없는 상태**다. 여기서 "[전반 시작] 버튼"을 주면 두 경우뿐인데
  둘 다 나쁘다:
  - **아직 준비 안 됨** → 눌러도 갈 곳이 없다(=먹통 버튼). 실제로 서버가 `FIRST_HALF` 를 열기 전엔
    하프 로그 조회도 409 다(`logAvailableFor`).
  - **이미 준비됨** → 서버가 `FIRST_HALF` 를 열면 **재생 창이 이미 흐른다**(`phase_ends_at` 은 그
    순간부터 카운트). 유저가 버튼 앞에서 머문 만큼 전반 앞부분이 **되돌릴 수 없이** 날아간다
    (플레이 모드엔 컨트롤이 0개 — #216/#148 — 이라 되감을 수단이 유저에게 없다).
  - 실측 감각: 창 220s 에 하프 1350틱이므로 **벽시계 1초 ≈ 게임 6.1초**. 버튼 앞 10초 = 전반 1분 소실.
- 그래서 **B1·B3 의 끝맺음은 자동**이고, "닫혔다"는 감각은 **킥오프 비트**가 준다(§4.3).

### 4.2 왜 B2·B4 는 유저 버튼인가

- 두 지점은 **방금 끝난 단계**를 닫는 자리다. 다음 단계(감독시간/결과)는 이미 열려 있거나 즉시 연다 →
  **닫으면 갈 곳이 있다.** 그래서 버튼이 성립한다.
- ⚠️ 단, **B2 동안 감독시간(3분)이 흐른다.** 서버 창은 늘릴 수 없다(§2.1). 그러므로:
  - 카드가 **남은 감독시간을 표시**한다(`useCountdown` + `countdownLabel` 재사용 — `HalftimePanel`
    이 쓰는 그것). 손해가 보이면 유저가 스스로 닫는다.
  - **자동 소멸(백스톱)은 두지 않는다.** 대신 §4.4 의 "내용은 현재 상태가 정한다"로 안전을 얻는다 —
    감독시간이 만료돼도 카드가 거짓말하지 않고 **다음 단계를 가리키게 바뀐다**.
- **B4 는 시간 압박이 0** 이다(`FINISHED` 는 터미널). 끝맺음의 본체이므로 여기가 가장 강한 종결이다.

### 4.3 킥오프 비트 (B1·B3 의 끝맺음 표현)

- `GEN1→FIRST_HALF`, `GEN2→SECOND_HALF` 전이에서 **1.2초짜리 비트 카드**를 띄운다:
  큰 글씨 `전반 시작` / `후반 시작`, 백드롭 없음(경기 화면이 뒤에 비친다), **자동 소멸 + 클릭 시 즉시 소멸**.
- 비용 = 1.2초(≈ 게임 7초). 그래서 **길이는 config 상수**이고 `0` 이면 비트가 아예 없다(조정 포인트 §8-1).
- 비트는 같은 `MatchFlowOverlay` 가 `kind:"beat"` 로 렌더한다 — 오버레이 컴포넌트가 둘이 되지 않게.

### 4.4 stale 방어 — **열림은 전이가, 내용은 현재 상태가 정한다**

브릿지 카드는 열릴 때 문구를 **스냅샷하지 않는다**. 매 렌더에서 `match.state`(+`match.auto`)로부터
본문·CTA 라벨·이동 목적지를 파생한다. 결과:

| 상황 | 카드가 말하는 것 |
|---|---|
| B2 열림, state=`HALFTIME`, 오토 OFF | `이제 감독시간입니다` + `남은 감독시간 2:47` · CTA `감독시간으로` |
| B2 열림, state=`HALFTIME`, 오토 ON | `감독시간 없이 곧 후반이 시작됩니다` · CTA `후반 준비로` |
| B2 를 안 닫은 채 감독시간 만료 → state=`GEN2` | `후반을 준비하고 있습니다` · CTA `후반 준비로` |
| B2 를 안 닫은 채 → state=`SECOND_HALF` | `후반이 이미 시작됐습니다` · CTA `후반 보기` |
| B4, state=`FINISHED` | `경기가 끝났습니다` + 승패 · CTA `보상 받기`(`matchEndContinuation` 있으면) / **`보상과 결과 보기`** |

⚠️ 이 규칙이 **오토 모드 특수분기를 0으로 만든다**. 오토는 `HALFTIME` 이 0초라 B2 가 뜬 직후
상태가 `GEN2`→`SECOND_HALF` 로 달려가는데, 내용이 상태 파생이므로 카드가 알아서 따라간다.
"오토면 B2+B3 를 병합한다" 같은 코드가 필요 없다 — **자연히 한 장으로 읽힌다.**

### 4.5 `POST /skip` 재사용 검토 — **B2 에서는 쓰지 않는다**

프롬프트 검토 항목("전반 종료 브릿지에서 '바로 후반' 같은 것")에 대한 답:

- `/skip` 의 바디는 `phase: FIRST_HALF|SECOND_HALF` 이고 CAS 가 `WHERE state=:phase` 다. 즉
  **감독시간(`HALFTIME`)에는 쓸 수 없다**(409). 감독시간을 건너뛰는 기존 수단은 **`POST /resume`**
  (=[후반 시작] 버튼)이고 그건 `HalftimePanel` 이 이미 소유한다.
- 그러므로 B2 브릿지에 "바로 후반" 버튼을 넣는다면 그건 **`/resume` 의 두 번째 호출부**가 된다.
  → **넣지 않는다.** 이유 = `auto-mode.ts` 가 감독시간에서 오토 토글을 뺀 것과 **같은 규칙**:
  *"그 화면엔 [후반 시작]이 이미 있어서 같은 일을 하는 컨트롤이 둘이면 유저가 뭘 눌러야 할지 모른다."*
  B2 를 닫으면 곧바로 그 버튼이 있는 감독시간 화면이다. 한 번 더 누르는 비용 < 컨트롤이 둘인 비용.
- 다만 **B2 의 CTA 라벨이 그 다음 행동을 예고**한다(`감독시간으로`) — 유저가 "닫으면 뭐가 오는지"를
  안 채로 닫는다. 이것이 요구 ①("다음 스텝 설명")의 실현이다.

### 권장 = **A**

이유 셋:
1. **가장 싸고 회귀 표면이 가장 작다.** W2 가 이미 카드 스택(뒤 카드 그림자 `MAX_BEHIND=2`,

2. **닫기가 하나면 충돌이 없다.** 에픽이 경고한 "전환 지점에서 두 화면이 충돌한다"가 구조적으로 사라진다.
3. **종결감 약화는 값으로 보완된다** — 브릿지 카드에 `data-card="bridge"` 를 주고 시각을 다르게

Escape·백드롭 클릭이 어느 층을 닫는지). `common/Modal` 은 트랩/복원을 소유하므로 두 개를 겹치면
그 계약을 다시 검증해야 한다. 얻는 것(약간의 종결감)보다 잃는 것이 크다.

## 6. 트리거·큐·중복 제거 (구현 규칙)

### 6.1 전이 관측

```ts
// flow/useMatchFlow.ts (신규)
const prevRef = useRef<string | null>(null);
useEffect(() => {
  const next = match?.state;
  const prev = prevRef.current;
  prevRef.current = next ?? null;
  if (!next || prev == null || prev === next) return;   // ← 첫 관측은 발화하지 않는다
  const bridge = bridgeForTransition(prev, next);        // 순수(match-flow.ts)
  if (bridge) open(bridge);
}, [match?.state]);
```

- ⚠️ **첫 관측(`prev == null`)에서는 절대 열지 않는다.** 이것이 "새로고침·재입장에 브릿지가 다시
  뜨지 않는다"의 **구조적** 보장이다(플래그 저장소 없이). `FINISHED` 매치를 나중에 다시 열어도
  B4 가 안 뜬다 — 이미 본 경기이므로 옳다.
- 폴링 주기는 라이브 1초(`pollIntervalFor`)이므로 전이 관측 지연 상한도 1초다.

### 6.2 스킵 경로와의 합류 — **같은 큐, 키로 중복 제거**

`useSkipHalf` 성공 → `setQueryData(["match", id], match)` 로 캐시가 즉시 갱신되므로 §6.1 의 전이
관측도 **같은 프레임에 발화**한다. 두 소스가 하나의 큐에 들어가고 `kind` 로 합쳐진다:

```ts
open({ kind: "h1_end", report: 1 })   // ← SkipButton.onSkipped (리포트 카드 포함)
open({ kind: "h1_end" })              // ← 전이 관측 (리포트 없음)
// 규칙: 같은 kind 가 이미 열려 있거나 이미 소비됐으면 **무시**. report 는 병합(있는 쪽이 이긴다).
```

- 소비 이력 `seen: Set<BridgeKind>` 를 매치별로 들어 **닫은 브릿지가 폴링으로 다시 열리지 않게** 한다.
- 두 소스의 **순서에 의존하지 않는다**(React Query 는 훅 옵션 `onSuccess` → mutate 콜백 `onSuccess`
  순서라 스킵 신호가 전이 관측보다 늦을 수 있다). 그래서 `report` 를 **나중에 병합**할 수 있게 둔다:
  이미 `h1_end` 가 열려 있는 상태에서 `report:1` 이 오면 카드 배열 앞에 리포트를 **끼워 넣는다**
  (사용자가 아직 첫 장을 보고 있으므로 인덱스 0 유지 = 리포트부터 읽게 된다).
  ⚠️ 이 병합 규칙은 순수 함수(`mergeBridge`)로 두고 계약을 박는다 — 인라인으로 쓰면 순서 의존이 되살아난다.

### 6.3 브릿지 종류(키)

```ts
export type BridgeKind = "match_start" | "h1_end" | "h2_start" | "match_end";
export type BeatKind   = "kickoff_h1" | "kickoff_h2";
```

| 키 | 전이 | 형태 |
|---|---|---|
| `match_start` | `BRIEFING→GEN1` | 패널(GenWaitPanel) — 오버레이 큐에 **안 들어간다** |
| `kickoff_h1` | `GEN1→FIRST_HALF` | 비트(오버레이, 자동 소멸) |
| `h1_end` | `FIRST_HALF→{HALFTIME,H1_BREAK,GEN2,SECOND_HALF}` | 오버레이 카드 |
| `h2_start` | `{HALFTIME,H1_BREAK}→GEN2` | 패널(GenWaitPanel) — 큐에 **안 들어간다** |
| `kickoff_h2` | `GEN2→SECOND_HALF` | 비트 |
| `match_end` | `{SECOND_HALF,GEN2,HALFTIME,H1_BREAK,FIRST_HALF,GEN1,BRIEFING}→FINISHED` | 오버레이 카드 |

⚠️ `h1_end`·`match_end` 의 집합이 넓은 이유 = **관측 누락**이다(§4 표 아래 문단이 SoT). `to` 는
그대로 좁다 — `match_end` 의 문은 `FINISHED` 하나뿐이라 몰수(`ABANDONED`)·사고(`FAILED`)는 안 걸린다.
**소스 SoT 는 `apps/web/src/match/flow/match-flow.ts` 의 `BRIDGE_TABLE` 이고 이 표는 그 사본이다** —
표만 보고 되돌리지 말고 그 파일 주석의 근거를 먼저 읽어라.

⚠️ **대기형(B1·B3)이 큐에 안 들어가는 것이 요점**이다 — 그 화면은 이미 패널로 존재하고,
오버레이로 또 덮으면 `GenWaitPanel` 의 경과 시계·[경기 포기](#217 AC3)가 가려진다.

### 6.4 서버 상태를 앞지르지 않는다

- 오버레이는 **어떤 서버 호출도 하지 않는다.** 닫기 = 로컬 상태 해제뿐. 브릿지가 전이를 일으키는
  경로는 0이다(전이는 스위퍼/유저 액션 버튼/스킵만).
- 그래서 "브릿지를 닫았는데 갈 곳이 없다"가 불가능하다 — 닫으면 **그 순간의 `panelForState` 결과**가
  그대로 뒤에 있다.

## 8. D6 갭 해소 — 오버레이 마운트 지점 승격 (요구 ⑤)

### 문제 (#421 W2 가 남긴 것)

스킵 응답이 `GEN2`(오토 ON + h2 프리페치 미완)면 `panelForState("GEN2") === "genwait"` 이라
`MatchPage` 가 `GenWaitPanel` 로 라우팅한다 → **`StageShell` 언마운트** → 거기 마운트돼 있던
`HalfReportModal` 이 같이 사라진다. 에러는 아니지만 **유저가 리포트를 못 본다**.

### 확정

**흐름 오버레이의 소유자는 `MatchPage` 다.** `StageShell` 은 오버레이를 소유하지 않는다.

```tsx
// MatchPage.tsx (개념)
const flow = useMatchFlow(match);                       // 전이 관측 + 큐

const overlay = <MatchFlowOverlay flow={flow} match={match} … />;

if (match && (panel === "live" || panel === "halftime" || panel === "result")) {
  return <>
    <StageShell … onSkipped={flow.openReport} />
    {overlay}
  </>;
}
return <>
  <Layout header={header}> … {panel === "genwait" && <GenWaitPanel match={match} />} … </Layout>
  {overlay}
</>;
```

근거 셋:
1. **패널이 바뀌어도 오버레이가 산다** — 이 갭의 직접 해소. 브릿지도 정확히 같은 문제를 겪는다
   (B2 를 열어 놓고 감독시간이 만료되면 `HALFTIME`→`GEN2` 로 패널이 갈린다).
2. **브릿지는 경기 _전체_ 흐름이다** — 관전 셸의 부품이 아니라 매치 단위 개념이므로 소유자도 매치 단위여야 한다.
3. **`StageShell` 의 편집이 줄어든다**(#406 충돌 최소화) — 오히려 #421 이 넣은 블록을 걷어낸다.

⚠️ **`StageShell` 안의 무대 언마운트 가드는 유지한다.** #421 은 *"리포트가 떠 있는 동안 무대를
렌더하지 않는다"*(`reportHalf == null &&`)를 넣어 캔버스를 구조적으로 멈춘다. 소유자가 올라가면
그 신호도 위에서 내려와야 한다 → `StageShell` 에 `overlayOpen?: boolean` prop 1줄로 관통하고
조건을 `!managing && !overlayOpen` 으로 바꾼다(편집 2줄). **정지 플래그를 뷰어에 새로 만들지 않는다**

### 9.1 타입 (SoT = `apps/web/src/match/flow/match-flow.ts`, #424 소유)

```ts
/** 경기 종료 브릿지가 후속 흐름에 넘기는 전부. 여기에 없는 것은 소비자가 스스로 조회한다. */
export interface MatchEndHandoff {
  /** 이 매치의 id — 소비자는 이것으로 자기 데이터를 조회한다(보상/성장은 #405 소관). */
  matchId: string;
  /** 항상 "FINISHED". 브릿지는 서버 상태를 앞지르지 않으므로 이 값이 곧 보증이다. */
  matchState: "FINISHED";
  /** 이 종료가 유저의 스킵으로 앞당겨졌나 — 연출 길이를 줄이는 판단에 쓸 수 있다. */
  viaSkip: boolean;
  /** 서버 확정 스코어(모르면 null). 소비자가 다시 조회할 필요를 줄이는 편의값이다. */
  score: { home: number; away: number } | null;
  /** "WIN" | "DRAW" | "LOSS" | null — MatchDetail.result 그대로. */
  outcome: string | null;
}

/**
 * 경기 종료 브릿지의 **다음 화면** 확장점(현재 호출부 0 — 위 정정 참조).
 * - 넘기지 않으면 브릿지 CTA 라벨은 `보상과 결과 보기` 이고, 누르면 오버레이가 닫혀 보상 시트
 *   (미확인 봉투가 있을 때) → FINISHED 결과 탭이 보인다.
 * - 넘기면 CTA 라벨이 `보상 받기` 로 바뀌고, 누른 순간 **같은 오버레이 안에서** 이 노드가 렌더된다.
 *   `onDone()` 을 부르면 오버레이가 닫히고 결과 탭으로 간다.
 */
export type MatchEndContinuation = (
  handoff: MatchEndHandoff,
  onDone: () => void,
) => React.ReactNode;
```

### 9.2 배선

#### 9.2.a 실제 출하 형태 (main `4095cff` 이후 — **이것이 현재 사실이다**)

`MatchPage` 는 `matchEndContinuation` 을 **넘기지 않는다**. 대신 두 오버레이가 `overlayOpen`
한 축으로 순서를 잡는다.

```tsx
// MatchPage.tsx — 오버레이 소유자(D6). continuation 은 비어 있다.
<MatchFlowOverlay flow={flow} … />
<StageShell … overlayOpen={flow.overlayOpen} />

// StageShell.tsx — 시트는 셸이 소유하고, 브릿지가 떠 있는 동안은 열지 않는다.
const showRewardSheet =
  Boolean(bundle) && !overlayOpen && ((shouldShowRewardSheet(bundle) && !sheetDismissed) || sheetReopened);
```

- **미룰 뿐 삼키지 않는다** — 게이트는 다른 항을 건드리지 않으므로 봉투가 미확인인 한 브릿지를
  닫은 뒤 반드시 뜬다. 그래서 C6(`FINISHED` 재입장엔 브릿지가 없다)에서도 시트는 평소대로 뜬다.
- 이 형태를 고른 이유 = 두 오버레이가 **같은 순간**(`FINISHED`)에 자동으로 뜨는데 게이트가 없으면
  `common/Modal` 포커스 트랩이 2겹이 되기 때문(설계 §3.2 *"하나의 카드 스택, 하나의 닫기"* 가 이미
  기각한 사고 유형). 순서는 **브릿지가 앞**이고, 그것이 `nextHint`(`다음 · 경기 보상과 결과 확인`)와
  CTA(`보상과 결과 보기`)가 예고하는 화면과 일치한다.

#### 9.2.b 원 설계안 (미착지 — 확장점으로 남는다)

```tsx
// MatchPage.tsx — 이 prop 을 채우면 CTA 가 `보상 받기` 가 되고 오버레이 **안에서** 렌더된다.
<MatchFlowOverlay
  …
  matchEndContinuation={(h, done) => <RewardFlow matchId={h.matchId} onDone={done} />}
/>
```

⚠️ 두 형태는 배타적이지 않다 — 9.2.b 를 채우면 브릿지 CTA 가 시트 대신 그 노드를 열고, 그 노드가
`onDone()` 을 부른 뒤에야 `overlayOpen` 이 내려가 9.2.a 의 시트가 (아직 미확인이면) 뜬다.

| P4 | 스킵 신호가 **늦게** 와도 리포트 카드가 앞에 끼워진다(순서 무의존) | `mergeBridge` 를 "이미 열려 있으면 무시"로 축소 |
| P5 | 닫은 브릿지는 폴링이 다시 열지 않는다(`seen`) | `seen` 제거 |
| P6 | **오토 모드**에서 `FIRST_HALF→GEN2` 직행도 `h1_end` 를 연다 | 전이표에서 `GEN2`/`SECOND_HALF` 타겟 제거 |
| P7 | 카드 본문·CTA 가 **현재 state 파생**이다(열림 시점 스냅샷 아님) | 본문을 open 시점에 문자열로 굳히기 → 감독시간 만료 후 거짓말 |
| P8 | `onDone` 멱등(C4) | 중복 호출 가드 제거 |

## 14. 미해결 · 후속

1. **B2 의 감독시간 잠식** — 브릿지를 읽는 시간만큼 3분이 줄어든다. 서버 창을 늘릴 수단이 없으므로
   (§2.1 되감기 불가) 표시로만 완화했다. 잠식이 실사용에서 문제가 되면 선택지는
   ⓐ 백스톱 자동 소멸(조정 포인트 4) ⓑ 서버가 `HALFTIME` 창을 브릿지 표시분만큼 늦게 여는 API
   (= 서버 변경, 별도 이슈) 둘이다. **지금은 ⓐ 의 자리만 비워 둔다.**
2. **킥오프 비트의 재생 손실**(1.2초 ≈ 게임 7초). 비트를 0 으로 두면 사라지지만 B1·B3 의 끝맺음
   표현도 같이 사라진다 — 트레이드오프를 hero 가 본 뒤 정한다.
3. ~~**`#405` 미머지 상태의 B4** = `결과 보기` 폴백. 이것이 선배포 형태다(C2).~~
   → **해소·정정(W6)**: #405 는 머지됐지만 `matchEndContinuation` 이 **아닌** 방식(§9.2.a)으로
   착지했다. 그래서 그 prop 은 여전히 호출부 0 이고, 출하되는 CTA 는 `보상과 결과 보기` 다.
   **남은 것 = "그 확장점을 언제까지 들고 갈 것인가"** — 지금은 C2~C5 계약이 태우고 있어 죽은
   코드가 아니지만, 소비자가 끝내 안 생기면 회수를 검토한다(그때도 C2 가 선배포 근거였음을 같이 본다).
4. **평점 카드**(#403 어댑터)는 여전히 `null` 스텁 — 스택이 1장 줄 뿐 브릿지 흐름과 무관(#421 W2).
5. **관측 누락으로 넓힌 `from`/`to` 는 근본 해결이 아니다.** 탭이 백그라운드인 동안 React Query 가
   폴링을 멈추는 것이 원인이라, 넓히기는 "마지막 관측에서 곧바로 종료가 보이는" 경우를 받아 주는
   것일 뿐 **중간 지점(B2 등)은 그 경기에서 영영 안 뜬다**. 서버가 "내가 놓친 전이 목록"을 말해 주지
   않는 한 클라만으로는 닫히지 않는다 — 별도 이슈감.
