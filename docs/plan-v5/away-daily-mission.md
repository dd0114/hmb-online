# 원정 데일리 미션 — 설계 (에픽 #408, W1 게이트 산출물)

> hero 요구(2026-08-02, 메가 에픽 요구 11): *원정경기 데일리 미션 — 하루마다 초기화되는 미션 **2개**, 달성 시 보상.
> 미션은 **랜덤**, 보상은 미션에 따라 결정, **보상은 전부 다이아**. 예: "원정 2연승 = 200다이아" · "한 경기 3골 달성" ·
> "총 3승 달성". **하스스톤 데일리 미션 참고.** 처음 미션 2개가 주어지고 **각각 한 번씩 리롤** 가능.*
>
> 이 문서 = **hero 컨펌을 받기 위한 설계안**. 컨펌 전에는 구현하지 않는다.
> 읽는 사람이 이 에픽을 처음 본다는 전제로 썼다 — §1 이 "왜 지금 이걸 만드나", §7 이 "결정해 주셔야 할 것".

## 2. 레퍼런스 — 하스스톤은 무엇을 하고 있나

hero 가 지정한 레퍼런스. 우리 요구와 다른 지점을 굵게 표시했다.

| | 하스스톤 | 클래시 로얄 | 마블 스냅 | **HMB (요구)** |
|---|---|---|---|---|
| 동시 보유 | 3개(꽉 차면 그날 지급분 소멸) | 3개 | 다수 | **2개** |
| 리롤 | **하루 총 1회** | 하루 1회 무료, 이후 10젬 | — | **미션당 1회 = 하루 2회** |
| 리셋 | 서버 현지 자정 | 일 단위 | 일 단위 | KST 자정(제안) |
| 보상 티어 | 800~900 / 1,000 / **1,500**(프리미엄) | 상자(변동) | **50 / 100**(정확히 2배) | 티어별 다이아 |
| 티어 비율 | 기본 대비 **1.7~1.9배** | — | **2배** | **1 : 2 : 3**(제안) |
| 풀 크기 | 65종 | — | — | 14종(제안) |

**읽어낸 것 3가지**

1. **"판수형(쉬움) < 승수형(보통) < 특수조건(프리미엄)"** 3단 구조가 공통이다.
2. 티어 간 보상 배율은 **1.7~2배**로 수렴한다 — 난이도 대비 보상이 지나치게 가파르면 쉬운 미션이 무의미해지고,
   평평하면 어려운 미션을 할 이유가 없다.
3. 하스스톤은 리롤이 **하루 총 1회**인데 우리 요구는 **미션당 1회**다. 더 관대하다 — 이게 문제가 되는지는 §6.2 에서 다룬다.

## 3. 실측 — 미션 난이도를 추측하지 않기 위해

미션 임계값을 감으로 잡으면 "아무도 못 깨는 미션"이나 "그냥 주는 미션"이 된다. 라이브 경기 데이터로 실측했다.

### ⚠️ 표본 경고 — 먼저 읽어야 한다

| | 값 |
|---|---|
| FINISHED 매치 전체 | 74 |
| **그 중 원정** | **16** (유저 7명, user-day 10개) |
| 기간 | 2026-07-21 ~ 08-02 |

**원정 16경기 중 11경기(69%)가 단 2명에게서 나왔다.** 원정 백분율의 95% 신뢰구간은 ±20~25%p 다.
아래 수치는 **자릿수 감**이지 정밀값이 아니다. 그래서 이 설계는 실측을 **티어 분류에만** 쓰고,
**금액은 실측이 아니라 §1 의 가격 앵커에서 끌어온다**(표본이 흔들려도 보상표가 흔들리지 않도록).

데이터 무결성 자체는 3중 교차검증을 통과했다 — 파생 승패 74/74 = 저장된 `result`, 원정 16/16 = `away_reports` 미러,
매치로그 골 합계 74/74 = 스코어 컬럼. **수치는 정확하고, 표본 크기만 문제다.**

|---|---|---|
| 승 / 무 / 패 | **43.8% / 0% / 56.3%** | **무승부 0건** |
| 팀 득점 평균 | 1.63골 | 실점 1.88 |
| 한 경기 2골 이상 | **37.5%** | |
| 한 경기 3골 이상 | **31.2%** | |

### 3.2 🔴 하루에 치는 원정 판수 — 이게 가장 센 제약이다

원정 user-day 10개 전수:

| 하루 원정 판수 | 도달 user-day |
|---|---|
| ≥1판 | 10 / 10 (**100%**) |
| **≥2판** | **3 / 10 (30%)** |
| ≥3판 | 2 / 10 (20%) |
| ≥4판 | 1 / 10 (10%) |
| ≥5판 | **0건** |

중앙값 = **하루 1판**. 즉 **"원정 2승"·"2연승"류는 오늘의 전형적인 유저에게 물리적으로 불가능하다.**

⚠️ 다만 이건 **인과가 아니라 현상**이다. 지금 원정을 더 칠 이유가 없어서 안 치는 것이고,
원정 일일 한도는 **10판**이라 여유는 충분하다. 데일리 미션이 바로 그 이유를 만드는 장치다.
그래도 **"오늘 절대 못 깨는 미션 2개"는 리텐션에 마이너스**이므로, §5.1 에서 **슬롯 A 를 1판짜리로 고정**한다.

### 3.3 🔴 "한 선수 N골" 미션은 성립하지 않는다

매치로그의 골 이벤트를 (경기·팀·선수)로 집계한 결과:

| | 원정 | 전체 |
|---|---|---|
| P(한 선수 2골 \| 팀 2골 이상) | **6/6 = 100%** | 35/36 = **97%** |
| P(한 선수 3골 \| 팀 3골 이상) | **5/5 = 100%** | 20/21 = **95%** |

팀이 4골 넣은 5경기는 **전부 한 선수가 4골을 넣었고**, 7골 넣은 2경기도 **한 선수가 7골**이었다.
엔진이 스트라이커 한 명에게 득점을 몰아준다 → **"한 선수 2골" 미션 ≈ "팀 2골" 미션**이라 별도 티어로 구분되지 않는다.
⇒ **개인 득점 미션은 풀에서 제외**한다(엔진의 득점 분산이 개선되면 그때 다시 본다 — 엔진 트랙 #407 소관).

## 5. 보상표

### 5.1 배분 규칙 — 슬롯 A 는 반드시 1판짜리

```
슬롯 A = T1 풀에서 1개                       ← 오늘 1판만 쳐도 뭔가는 받는다
슬롯 B = T2 70% / T3 30% 가중 추첨            ← 오늘의 도전 과제
```

§3.2 가 이유다. 중앙값 유저는 하루 1판을 친다 — **두 미션이 모두 3판을 요구하면 그날 보상은 0** 이 되고,
그건 "미션이 생겼는데 아무것도 못 받았다"라는 최악의 첫인상이다.
슬롯 A 고정은 **하루 상한도 같이 고정**한다(100+300 = 400 Z 이상 나올 수 없다).

> 대안 = **완전 랜덤 2개**(중복만 금지). 변동폭이 커져(하루 200~600 Z) 뽑기의 재미가 붙지만,
> "오늘 둘 다 못 깨는 날"이 실제로 생긴다. §7 Q2 에서 판단을 구한다.

### 5.2 금액 — 3안 비교

| | 쉬움 | 보통 | 어려움 | 하루 최대 | 하루 기대(전부 달성) | **10연(3,000 Z)까지** | 30일 최대 |
|---|---|---|---|---|---|---|---|
| A 보수 | 50 | 100 | 150 | 200 | 165 | **18일** | 6,000 |
| **B 권장** | **100** | **200** | **300** | **400** | **330** | **9일** | 12,000 |
| C 관대 | 150 | 300 | 500 | 650 | 510 | **6일** | 19,500 |

**B 를 권장하는 근거 4가지**

1. **hero 의 앵커와 정확히 맞는다.** 요구에 적힌 *"원정 2연승 = 200다이아"* 에서 2연승은 T2 다 → T2 = 200.
   나머지는 업계 수렴 배율(1:2~1:3)로 채운 것이라 앵커를 흔들지 않는다.
2. **한 달 꼬박 하면 가입 지급 1회분.** 30일 최대 12,000 Z = 라이브 가입 지급(12,000 Z)과 같다.
   "매일 하면 한 달에 스타터 팩 하나를 더 번다"는 체감은 설명하기 쉽고 과하지 않다.
3. **A 는 문제를 못 고친다.** §1 의 실태(잔액 0 인 유저가 13명)에서 하루 165 Z 는 10연 한 판에 18일이다.
   지금 실수입이 30~90 Z/일이라 개선이긴 하지만, 수도꼭지를 여는 게 목적인데 물이 안 나온다.
4. **C 는 되돌리기가 어렵다.** 보상은 **올리기는 쉽고 내리기는 매우 어렵다**(내리면 너프로 읽힌다).
   금액이 전부 config 노브라 무배포로 올릴 수 있으므로, **B 로 열고 데이터를 보고 올리는** 쪽이 안전하다.

### 5.3 다른 다이아 축과의 서열 — 이 순서가 깨지면 의도가 무너진다

| 축 | 하루/회당 | 미션(B안) 대비 |
|---|---|---|
| 미션 하루 상한 | **400 Z** | — |
| 리그 일일 트랙 이론 최대 | 1,080 Z | 미션이 **0.37배** ✔ |
| 리그 일일 트랙 **실측** | 30~90 Z | 미션이 4~13배 ⚠️ |
| 리그 시즌 완주 | 3,000 Z | 미션 **7.5일치** ✔ |
| 리그 우승(1위) | 9,000 Z | 미션 22.5일치 ✔ |

⚠️ **미션이 리그 일일 트랙의 실측치를 4~13배 앞선다.** 이건 부작용이 아니라 **의도한 결과**다 —
리그 트랙은 하루 18칸이라 실플레이(1~4.5판)로는 닿지 않는 설계고, 미션은 1~3판에 맞춰 설계했다.
다만 **"리그를 열심히 하는 것보다 원정 미션 두 개가 낫다"** 가 되면 리그의 위상이 흔들리므로,
**계약으로 서열을 박제**한다: `미션 하루 상한 < 리그 일일 트랙 이론 상한` · `미션 하루 상한 × 7 < 리그 시즌 완주 + 우승 보너스`.
이 관계가 깨지는 노브 조정은 의도한 것이어야 하고, 그때 테스트가 먼저 깨진다(#368 이 쓴 방식 그대로).

## 6. 규칙

### 6.1 리셋 — KST 자정, 그런데 **리셋 잡은 만들지 않는다**

기존 일일 경계와 같은 기준을 쓴다: 원정 일일 한도(10판)·선수 컨디션·리그 일일 트랙 전부 **KST 자정**이고,
SoT 는 `ConditionService.dateOf(instant)` 다. 체감이 어긋나면 "어제 것"의 의미가 화면마다 달라진다.

⚠️ **리포에 "00:00 KST 에 도는 잡"이 하나도 없다.** 일일 의미는 항상 현재 KST 날짜로 lazy 계산한다.
미션도 **day-key 행**(`user_id, day`)으로 만들고, 자정이 지나면 **다음 조회 때 새 날짜의 행이 생긴다**.
리셋 스위퍼를 만들면 이 리포에서 유일하게 시계에 의존하는 부품이 되고, 서버가 잠깐 죽은 새벽에 조용히 건너뛴다.

**날짜 앵커는 경기 종료 시각**(생성 시각 아님). 23:58 에 시작해 00:03 에 끝난 경기가 어제 미션을 채우면
유저는 오늘 화면에서 그 판이 사라진 걸 본다. 이 버그류에 이 리포가 이미 두 번 당했다.

### 6.2 리롤 — 미션당 1회, 전체 풀에서 재추첨

- 리롤하면 **진행도는 0 으로 초기화**된다(하스스톤과 동일). 이미 보유 중인 다른 미션과 **중복 추첨 금지**.
- 이미 **달성한 미션은 리롤할 수 없다**(보상만 챙기고 새 미션을 받는 무한 루프가 된다).
- 리롤 횟수는 **미션 슬롯에 매인다** — 자정에 새 미션이 오면 리롤도 다시 1회씩.

**"쉬운 걸로 갈아타는 어뷰징"은 성립하지 않는다.** 보상이 티어에 비례하므로 어려운 미션을 굴려 쉬운 걸 뽑으면
**받는 다이아가 같이 줄어든다**. 즉 리롤은 이득이 아니라 **"달성 가능성 ↔ 보상"의 선택**이다.
이게 티어 비례 보상표를 쓰는 두 번째 이유다(첫째는 §2 의 업계 관행).

> 대안 = **같은 티어 안에서만 재추첨**. 하루 기대 보상이 완전히 고정돼 예측 가능해지지만,
> 리롤이 "문구만 바뀌는 버튼"이 돼 재미가 없다. 권장하지 않는다.

### 6.3 이월 — 미션은 이월 없음, **보상은 안 사라진다**

- **미완료 미션**: 이월 없이 자정에 교체(요구 문구 *"하루마다 초기화"* 그대로). 진행도도 사라진다.
- **달성했는데 안 받은 보상**: **기한 없이 남는다.** 미션 행이 그날 날짜로 박제돼 있고 `claimed_at` 이 비어 있으면
  다음 날에도 받을 수 있다.
  - 이유: 마지막 경기를 치고 앱을 껐다는 이유로 보상을 잃으면 그건 버그로 읽힌다. 우편함도 **만료 기본 무기한**이다.
  - 이 규칙 덕에 **"자정에 미수령분을 지급하는 잡"이 필요 없다**(§6.1 과 같은 이유로 잡을 만들지 않는다).

### 6.4 신규 유저 첫 지급

**첫 조회 시점**에 그날 미션 2개를 만든다(가입 시점이 아니라). 가입 시점에 만들면 가입만 하고 안 들어온 유저의
미션이 매일 쌓이고, 그건 §6.1 의 lazy 원칙과도 어긋난다. **원정을 한 번도 안 해 본 유저에게도 미션은 보인다** —
그게 원정으로 끌고 가는 장치다.

### 6.5 포기(ABANDONED)·몰수는 세지 않는다

자발 포기는 정산 경로(`finishMatch`)를 아예 지나지 않고, 기존 선례가 포기를 **연승·시즌·재화에서 전부 제외**한다.
미션도 같게 간다. 안 그러면 "출전 3회" 미션을 **포기 3번으로 클리어**할 수 있다.

### 6.6 수령 — 자동 판정 + 수동 수령

- **판정은 서버가 자동**(경기 정산 시점). 클라가 "달성했다"고 신고하는 경로는 없다.
- **수령은 유저 액션**(`받기`). 다이아가 지갑에 꽂히는 순간을 유저가 만든다.
- 수령 UI 는 **#405(E2)의 확장형 보상 탭**을 쓴다 — 원정 경기 직후면 결과 보상 탭에 "미션 달성" 섹션으로,
  그 외 시점이면 원정 페이지의 미션 목록에서. (인터페이스는 #405 에 코멘트로 조율 중.)

## 8. 기술 스케치 (참고 — 게이트 대상 아님)

컨펌 후 이 방향으로 구현한다. **전부 기존 선례 재사용이고 새로 발명하는 건 미션 상태 하나뿐이다.**

### 저장 — 왜 파생이 아니라 테이블인가

미션 진행도는 매일 `matches` 에서 다시 계산할 수도 있다. 그럼에도 **행을 박제한다**. 근거는 `league_daily_rewards`·
`starter_grants` 와 같다: **금액·티어·풀 구성이 전부 config 노브**라, 읽을 때마다 재계산하면 운영이 노브를 돌리는
순간 **오늘 이미 받은 보상의 이력이 소급 변조된다**("아까 200 받았는데 화면엔 100"). **`amount` 와 `tier` 를 행에 박제**한다.

```sql
CREATE TABLE daily_missions (
  id          TEXT PRIMARY KEY,          -- ULID
  user_id     TEXT NOT NULL,
  day         TEXT NOT NULL,             -- 'yyyy-MM-dd' (KST)
  slot_no     INTEGER NOT NULL,          -- 1 | 2
  mission_id  TEXT NOT NULL,             -- 'away_streak_2' 등 (카탈로그 키)
  tier        TEXT NOT NULL,             -- 'EASY'|'NORMAL'|'HARD'  (박제)
  currency    TEXT NOT NULL,             -- 'GEM'                   (박제)
  amount      INTEGER NOT NULL,          -- 그 미션의 보상액         (박제)
  progress    INTEGER NOT NULL DEFAULT 0,
  target      INTEGER NOT NULL,          -- 박제(카탈로그가 바뀌어도 오늘 목표는 안 바뀐다)
  completed_at TEXT, claimed_at TEXT, rerolled_at TEXT,
  created_at  TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE UNIQUE INDEX uq_daily_mission_slot ON daily_missions(user_id, day, slot_no);
CREATE INDEX idx_daily_mission_user_day  ON daily_missions(user_id, day);
```

- 마이그레이션 번호는 **main 배정**(리포 최고 V37, #405 도 V38+ 를 노려 충돌). `FlywayMigrationTest` 기대 목록에도 등록.
- 미션 추첨은 **시드 RNG**(`rngFromSeed(userId + day)`) — 결정론이라 "왜 이 미션이 나왔나"를 재현할 수 있다.

### 지급 — 새 원장을 만들지 않는다

`walletService.applyGems(userId, amount, "daily_mission", dailyMissionRowId)`.
멱등은 **3층**: ① 수령 CAS(`UPDATE … WHERE claimed_at IS NULL`) ② 슬롯 유니크 ③ 원장 `uq_gem_ledger_reason_ref`.
`V33__mailbox.sql` 의 규칙 그대로 — *"왜 다이아가 늘었나"의 답이 두 곳이 되면 안 된다.*

### 판정 훅

`MatchOrchestrator.finishMatch` 의 **FINISHED CAS 통과 이후**, 원정 정산(`awayService.settle`) 바로 옆.
`mode == "away"` 일 때만. 그 자리에서 `result`·`userGoals`·`oppGoals` 가 이미 계산돼 있다.
"선제골" 판정만 매치로그 파싱이 필요하고, 그건 `GrowthService.eventCountsByPlayer` 가 같은 트랜잭션에서 하는 일과 같다.

### 조회 계약 — 클라는 아무것도 계산하지 않는다

`GET /api/missions/daily` 가 **문구·진행도·목표·보상액·상태를 완성해서** 내려준다.
클라가 티어→금액을 다시 계산하면 노브를 돌린 순간 화면이 거짓말한다(#368 이 같은 이유로 18칸을 통째로 내려준다).
수령 = `POST /api/missions/{id}/claim`, 리롤 = `POST /api/missions/{id}/reroll`.

### 계약 (E2E-TDD — 구현 전에 박는다)

| 계약 | 무엇을 죽이나 |
|---|---|
| 자정 경계가 **KST** 이고 앵커가 **종료 시각** | UTC 경계 변이(이 리포가 두 번 당한 버그) |
| 금액이 **config 에서** 오고 **행에 박제**된다 | 상수 하드코딩 · 노브를 돌리면 지난 지급이 바뀌는 변이 (픽스처 금액을 발행값과 **다르게** 둬서 관측) |
| 수령 2회차가 지갑을 안 움직인다 | 멱등 3층 중 어느 하나라도 뚫림 |
| 리롤은 미션당 1회 · **달성한 미션은 리롤 불가** · 진행도 초기화 | 무한 리롤 · 보상 이중취득 |
| **포기한 경기는 진행도를 안 올린다** | "출전 3회"를 포기 3번으로 클리어 |
| 슬롯 A 는 항상 T1 · 하루 상한이 §5.3 서열을 안 깬다 | 배분 규칙 소실 · 경제 서열 역전 |
| **실제 원정 경기를 끝내면 진행도가 오른다**(전 경로) | **훅 제거** — 서비스 단위 계약만 있으면 아무도 안 부르는 상태가 전부 통과한다 |

전 계약은 **변이체 킬 검증**을 거친다(구현을 되돌리면 실제로 죽는지 확인). 이 리포에 "통과만 하는 장식 계약" 사고가 여러 번 있었다.

## 9. 되돌리기

- **끄기**: 미션 카탈로그 config 를 비우면 새 날짜의 미션이 생성되지 않는다(이미 받은 보상은 그대로).
  금액만 0 으로 내리는 방법은 **쓰지 않는다** — 미션은 뜨는데 보상이 0 이면 고장으로 읽힌다.
- **금액 조정**: economy 노브(무배포). 박제 규율 덕에 **이미 지급된 것은 소급 변조되지 않는다**.
- **코드 롤백**: `finishMatch` 의 한 줄 + 라우트 등록 + web 섹션 한 줄.
