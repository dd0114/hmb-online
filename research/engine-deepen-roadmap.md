## 3. 구현 목록 — 웨이브별

> 순서 근거 = **의존 그래프**. `C5(수비 라인)` 없이 스루패스를 넣으면 라인이 상시 열려 있어
> "찌를 필요가 없다"(W1 §6.3 인과 루프 재현). `C2(런 의도)` 없이 크로스를 넣으면 낙하점에 아무도
> 없어 **크로스가 곧 턴오버**다. `C4(국면)` 없이 역습을 넣으면 모든 소유가 이미 역습 속도라 구분이 안 된다.
> 그리고 **W2 실험이 이미 증명했다** — 결정 로직만 고급화해도 선택지가 없으면 안 움직인다.

### W4 — 배선 회수 + 캐리·슛 방향 (난이도 **S~M**, 리스크 낮음)

**왜 먼저**: R5(죽은 노브)는 순수 배선이라 새 개념이 0이고, R3(방향 1개)는 `chain` 코어에서
**후보 배열 길이만 바꾸면 되는(구조 변경 0) 가장 싼 승리**다. 골든·밸런스 재보정 비용을 한 번에
몰지 않고 나누는 효과도 있다.

| 항목 | 지금 왜 안 되나 (파일:함수) | 어디를 고치나 | 새 개념 | config 노브 |
|---|---|---|---|---|
| **W4-1 죽은 노브 배선** | `movement.lineDiscipline`·`pressingScheme.triggerLine`·`team.width`·`SimPlayer.duty` 참조 0 | W5 에서 `teamplan.ts` 가 소비하도록 예약. **이 웨이브에서는 `team.width` 와 `duty` 만** — `decision.ts:decideOffBall` 공격/수비 폭 항에 `team.width` 를 곱하고, `duty` 로 전진런 계수 차등 | 없음 | 기존 재사용 |
| **W4-2 템포 실배선** | `team.tempo` 가 코너 가담도·오버랩에만. 이동속도(`speedStep`)는 pace·fatigue 만의 함수 | `decision.ts:decideBallOwner` 가중치 로드 직후 템포로 스케일(`wHold ×(1.5−tempo)` 등). **chain 코어에서는 `chain.discount` 를 `f(tempo)` 로** — 사슬에서는 템포가 곧 할인이다 | 없음 | `tempo: { holdWeightSpan, passWeightSpan, directnessSpan, chainDiscountSpan }` |
| **W4-3 캐리 방향 후보화** | `decision.ts:decideBallOwner` 드리블 목표 = 항상 `attackGoal`(x·y 둘 다 골 중앙으로 수렴) · `chain.ts` 동일 | 드리블을 **단일 목표 → 방향 후보 집합**(전방 반원 5방위). chain 은 각 후보를 `evaluateState` 로 채점(이미 채점기 보유) | `DribbleOption{toX,toY,kind}` | `attack.carry: { dirs, fanDeg, cutInBias, outsideBias }` |
| **W4-4 슛 조준점 분산** | 슛 목표 = 항상 `goal.x, goal.y` | 조준점을 골포스트 안쪽 ± 로 분산 | 없음 | `contest.shotAimSpreadM` |
| **W4-5 ⚠️ `central` 항 동반 수정** | `xgAtPoint` 의 `central`(`shootAngleFactor` 0.85)이 **횡방향을 강하게 벌한다** + `shootCentralBonus`(1.35)가 중앙을 부스트 → **새 방향 후보를 채점기가 전부 벌해 효과가 상쇄된다** | W4-3/4 와 **같은 커밋**이어야 한다 | 없음 | `shootAngleFactor` 재보정 |
| **W4-6 `spaceFactor` 섹터화** | 드리블 가중의 `spaceFactor` 가 **전방위 최근접 거리**라 "앞이 막혔는데 뒤가 비어서" 드리블 가중이 오른다 | 캐리 방향 ±60° 섹터 안 최근접으로 | `forwardSpace(player, dir)` | `movement.carry.sectorHalfAngleDeg` |

**판정 지표**: 슛 횡offset p90 **5.01 → ≥12m** · 9셀 엔트로피 **0.00 → ≥0.9** · 밴드 하드가드(골 1.4–1.8 · 패스성공률 78–85% · 슛 12–16 · 코너 4–6) 유지.
**리스크**: 슛 위치 분포가 바뀌면 xG 분포가 바뀐다 → **골든 전면 이동 + 다시드 재보정 확정**.

## 4. 웨이브 순서 — **hero 결정 반영(2026-07-30)**

### hero 결정 3건
1. **전부 적용한다. 순서는 "개발에 유리한 순"으로.**
2. **공중볼(C7)은 구현한다.** 단 **뷰어는 별도 트랙**으로 뺀다(엔진이 먼저, 렌더는 뒤따라온다).
3. **밸런스는 나중에.** 목표 = **경기당 골 평균 5골**(양팀 합).

### 그래서 순서를 바꿨다 — 의존 순서 → **개발 효율 순**

앞 절의 W4~W9 는 *의존 그래프* 순이었다. 전부 적용하기로 한 이상 그 순서의 최대 낭비는
**웨이브마다 60시드 밸런스 재보정을 반복하는 것**이다(매번 골든 대이동 + 독립 QA 재사이클).
전부 갈 거면 **구조를 먼저 다 넣고 밸런스는 마지막에 한 번**이 압도적으로 싸다.

| **S6** | **공중볼(C7)** — `BallFlight` 높이·딜리버리 종류 · 체공 · 헤더 경합 · 세컨볼 | 크로스(S5)가 있어야 공중볼이 쓸 데가 있다. **뷰어는 별도 트랙**(hero 결정) — 엔진은 데이터만 내보내고 렌더는 뒤따른다 | 공중경합 수 · 헤더골 비중 · 크로스 성공률 20–26% |
| **S7** | **세트피스 루틴** — 인/아웃스윙 · 숏코너 · 니어/파 · 박스 슬롯 · 프리킥 분기 · 롱스로인 | S6(공중볼) + S5(박스 슬롯)를 재사용. 벤치가 가장 촘촘해 마감에 적합 | 인/아웃스윙 xG 분리 · 숏코너 11–18% |
| **S8** | **밸런스 1회 + 최종 판정** | 구조가 다 들어온 뒤 **한 번만** 잡는다 | **경기당 골 5.0**(아래) · 구조 지표 유지 · 독립 QA |

### 배선 회수(구 W4-1/2)는 어디로?
**S3·S4 에 흡수**한다. `lineDiscipline`·`triggerLine`·`duty` 는 S3 의 라인/유닛이 **소비처**이고,
`team.width`·`tempo` 는 S4 의 국면/템포가 소비처다. 소비처 없이 먼저 배선하면 두 번 만진다.

### 밸런스 목표 (S8) — **리얼리즘 밴드를 골에는 적용하지 않는다**

| 지표 | hero 목표 | 실제 축구 | 비고 |
|---|---|---|---|
| **경기당 골(양팀)** | **5.0** | 2.7–3.3 | **hero 결정** — 1.5~1.9배. 게임 재미 우선 |
| 팀당 골 | ~2.5 | 1.4–1.65 | 위에서 파생 |

⚠️ **정직한 트레이드오프**: S3(수비 구조)가 들어오면 골은 **내려간다**(라인·협력압박이 생기니 당연).
5골을 만들려면 **찬스를 늘려서** 올려야 하고(크로스·컷백·스루패스 = S5), 그래도 모자라면
`xgBase`·`onTargetBase` 같은 마무리 확률을 올리게 된다. 후자는 "슛이 잘 들어가는 게임"이 되므로
**슛당 xG 벤치(0.10–0.12)는 포기 대상**임을 미리 명시한다.

**유지할 밴드(구조 지표 — 이건 리얼리즘 유지)**: 패스 성공률 78–85% · 다이렉트 스피드 ≤3.5 ·
팀 width 40–50m · 백4 산포 ≤6m · 크로스 10–14 · PPDA ≥4.
**포기/재설정하는 밴드**: 골 · 슛→골 전환 · 슛당 xG · 유효슛(골 목표에 종속).

**공통 게이트(매 스테이지)**: 구조 지표 판정 → 60시드 스윕(다시드 필수) → `qa-match`/`perceptibility`
→ E2E 계약 먼저 박제 → `npm test`(골든·desync 0·resume 동일·hygiene 0) → 실화면 캡처
→ **독립 QA 판정**. 밸런스 하드가드는 S8 까지 **골 상한만**(경기당 ≤8, 폭주 감지용) 건다.

## 5. 결정론 규율 (팀 단위 상태를 넣을 때 — 6조)

1. **계산은 decide 루프 앞, 틱당 1회.** `decideOffBall` 안에서 계산하면 안 된다 — 그 함수는
   `state.players` 순회 안에서 불리고 이미 `player.seen` 을 **변이**한다 → 배열 순서 의존이 생긴다.
2. **순수 함수 + Rng 0.** 롤이 필요하면 `varietyNoise`(시퀀셜 Rng 미소모) 또는 통짜/재개가 **똑같이
   도달하는 단 한 지점**에서만 소비.
3. **동률은 항상 전순서**(점수 → `idHash` → `id`). `state.players` 배열 순서에 기대면 안 된다 —
   퇴장이 splice 로 순서를 바꾼다. Map 순회 의존 금지.
4. **정수 고정소수만.** `Math.pow`/`exp`/`sin`/`cos` 런타임 금지(명세상 구현 근사 = 플랫폼 편차).
   필요하면 config 로드 시 굽는 정수 LUT. ※ **이건 이미 chain 코어에서 한 번 밟았고 수리했다.**
5. **같은 PR 에서 직렬화한다.** `SimState` 신규 필드 ⇒ 서버 `SimStateSchema` 선언 + **왕복 동등성 테스트**.
   zod 는 미선언 키를 **조용히 버린다**(#154 와 동형).
6. **해시에 넣어 desync 를 시끄럽게 만든다.** 현 `hashState` 는 tick·score·ball·possession·선수
   좌표/피로만 해싱한다 — 해시에 없는 상태가 유실되면 **그 틱은 통과하고 다음 틱부터 갈라진다**.

## 7. 1초 틱 한계

**결론: Tier C(0.25초) 승격은 이 로드맵 범위에서 불필요하다.** 62개 중 1초 틱이 실제로 막는 것은
**"같은 초 안의 2번째 접촉"** 계열 3개뿐이다 — 니어포스트 플릭온 · 컷백 후 원터치 마무리 ·
박스 난전(리바운드·세컨볼). 각각 2틱으로 늘려 표현하거나 확률 보정으로 흡수 가능하며,
Tier C 가 필요하다는 결론이 나면 **이 3개 항목만을 근거로** 별도 제안한다.

반대로 **카운터프레스 5초 룰은 1초 틱과 궁합이 좋다**(정확히 5틱).

## 8. 이 로드맵과 `chain` 코어의 관계

W2 실험(볼 소유자 결정만 사슬 탐색으로 교체)은 시퀀스 길이·패스 수는 개선했지만 다이렉트 스피드·
슛 위치는 **전혀 못 바꿨다**. 원인은 탐색기가 아니라 **후보 공간**이었다.

> **사슬 탐색은 버리지 않는다.** W4(방향 후보) · W7(좌표 타깃 생성기)이 들어오는 순간
> **고를 것이 생기고**, 그때 "이 행동이 도달하는 상태를 평가한다"는 구조가 비로소 값을 한다.
> 특히 스루패스·서드맨·원투는 사슬 탐색의 **정확한 사용처**다 — 성공 시 상태(라인 뒤 지점)의 가치와
> 실패 시 턴오버 비용이 자동으로 계산돼 **별도 노브 없이 리스크/보상이 나온다.**

현재 `chain` 코어는 `config.chain.mode` 스위치 뒤에 **꺼진 채로** 있고 골든에 영향이 없다.
각 웨이브에서 두 코어를 나란히 재측정해 채택 시점을 정한다.
